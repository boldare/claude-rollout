# rollout

A rollout is one plan shipped as several PRs. The orchestrator is a **process**, not a model: `bin/rollout.mjs run` ticks every minute, reads the truth from GitHub, starts headless agents (`claude -p`), checks the merge gate and merges. A model never drives the loop, so a stalled session cannot stall the rollout, and restarting the same command resumes from GitHub state plus the local ledger.

Everything lives in two places:

- this skill: its own directory, the installed copy (for example `~/.claude/skills/rollout/`), with the driver, prompts, schemas, guard hook, git hooks, docs and tests.
- one directory per rollout, outside any repo: `$ROLLOUT_ROOT/<name>/` (default `~/.rollouts`) with `manifest.yaml`, `briefs/<id>.md` (local only: they may name clients), `ledger.json` (versioned: the driver migrates an older one on start, and the driver, `status` and the UI refuse a newer one), `events.jsonl`, `heartbeat`, `driver.lock`, `driver.log`, `logs/`, `inbox/`. Its worktrees live next to it in `<name>.worktrees/`: `mirror.git`, a bare mirror of the repository's origin, and one clone of it per PR (`<id>/`) and per brief preview (`<id>.brief/`). Under `sandbox.runtime: docker` it also holds `<id>.home/` per PR, the home its implementer and fixes share, and `homes/`, the empty homes of every other run. Once every PR is merged the driver removes `mirror.git` and the empty `<name>.worktrees/`, and `clean` does it on demand. Besides its fetches, the driver creates or deletes nothing in `repo.path`.

`R` below is `bin/rollout.mjs` in this skill's directory. The full manual for people is `docs/index.html` in the same directory.

## Install

The repository is the skill: `SKILL.md` sits at its root. Clone it into the skills directory and install its one dependency:

```sh
git clone https://github.com/boldare/claude-rollout ~/.claude/skills/rollout
cd ~/.claude/skills/rollout && npm ci
```

A clone anywhere else works for the CLI alone. Never point the installed skill at a checkout someone develops in. The driver reads the prompts, schemas, guard and git hooks from its own directory on every agent run, so switching branches there changes a running rollout. To update, `stop` the driver, run `git pull && npm ci`, and `run` again.

## Identity and approvals

- `repo.agentToken` points to a token file of a separate GitHub account (write role, no ruleset bypass). It is a classic token with the `repo`, `workflow` and `read:org` scopes. Preflight fails a fine-grained token, which gets no Checks permission, and a token that cannot read `repo.github`. It warns without `workflow` or `read:org`. Agents get the token as `GH_TOKEN`, so they open PRs and push as that account. Under the host runtime it comes with an empty `GH_CONFIG_DIR`. A container gets no `GH_CONFIG_DIR` and has no stored login. Agents never get `GH_HOST`, because with it gh reads the maintainer's keyring login even from the empty config dir. They get `GH_REPO` pinned to `repo.github`, with or without a bot token. Worktrees push over HTTPS (`remote.origin.pushurl`, `gh auth git-credential`). The pre-push hook refuses any other URL, so the maintainer's SSH key is never used for pushes. The driver itself reads GitHub through its REST client (`lib/gh.mjs`) with the maintainer's token from `gh auth token`, and merges with `gh pr merge`, which runs with `GH_REPO` and `GH_HOST` pinned to `repo.github` on github.com.
- `policy.merge` (default `human`): `manual` (the driver verifies, gates, rebases and notifies "ready to merge"; the maintainer merges on GitHub and the driver carries on from the merge; one PR is ready at a time and carries `rollout-status:merge-by-hand`, the others wait with `rollout-status:queued`, their gate reason names the PR they wait for, and they are rebased and checked again once it merges. The queue only advises: GitHub still lets the maintainer merge a waiting PR. `hold` on the ready PR hands the slot to the next one), `human` (the driver merges after the maintainer's approval) or `auto`. Approval counts in the gate only under `human`: under `manual` the maintainer's merge is the approval, and `auto` needs none. `rollout approve` is refused under both.
- `policy.approval` (default `inbox`, which means `rollout approve`) or `github` with `repo.agentToken` and `repo.maintainers`: a PR from the agents' account counts as approved when a maintainer's latest review is APPROVED and was submitted after the current patch appeared, and no maintainer's latest review requests changes. Time, not the review's commit: GitHub moves a non-dismissed review's `commit_id` to new heads. Such PRs merge without `--admin` (`merge.admin: auto`). PRs a maintainer authored cannot be self-approved on GitHub, so they use `rollout approve` and the PR bypass.
- Under `human` the driver waits `policy.mergeDelaySeconds` (120 s) before merging. The wait counts from when the driver first sees the approval, never from a GitHub review's own time, and both channels notify at that moment. `hold <id>` in that window stops the merge. When GitHub's ruleset still blocks the merge, the gate waits instead of merging. A refused merge is logged as `merge-refused`, notifies once and waits for `retry`.
- Review comments by `repo.maintainers` (inline, review bodies and conversation) follow the `note` table once the maintainer has been quiet for `policy.feedbackQuietMinutes` (3), at every stage with a PR, a question or a dispute included, with the reason `maintainer-review` where a note gives `maintainer-note`. While an agent works on the PR, or the PR is closed, they wait unread. The driver replies in the threads as the agents' account, or as the maintainer without `repo.agentToken` (preflight warns when `repo.maintainers` is set). Its replies and summary comment end with a hidden `<!-- rollout-driver -->` line, and feedback collection skips comments ending with it. Comments by anyone else never reach an agent, bot comments included. Code scanning alerts reach the gate as data from the API instead (`repo.codeScanning`).

## Briefs written by the driver

A PR whose `brief` file does not exist gets one when each of its dependencies is merged, or verified and not held (`briefing.sources` in the manifest: the plan plus design notes, `tag`ged per track and picked by the PR's `briefTags`). A source's `kind` is `markdown` or `transcript`, the last long assistant text of a Claude Code JSONL. A relative `path` resolves against the driver's working directory, so use absolute or `~` paths. A read-only writer drafts it on a worktree of the current base, with the verified but unmerged dependencies merged in at their verified heads (a detached preview, `<id>.brief` next to the PR worktrees, that refuses every push and is removed afterwards), a read-only reviewer checks every path, line and command against that code and returns the final text, and the driver writes `briefs/<id>.md` plus `<id>.review-notes.md`. Heads that do not merge cleanly in the preview give the attempt back (`brief-waits`) until a dependency merges or is verified at another head. A dependency that merges with another patch than the brief saw is named in the implementer's prompt, where the code wins over the brief. Delete the brief file to have it written again. Brief runs use `effort.brief` (default `xhigh`). Open product questions stop the PR on `brief · needs-you: brief-questions`. `note <id> "<answers>"` gives the brief attempt back and re-runs the writer and the reviewer, which see every earlier question with its answer until the brief is written. The brief's expected files become the PR's scope when the manifest has none.

`gates.brief` checks every brief the driver writes. With `runChecks`, the reviewer runs the draft's existing verification and acceptance commands in the brief's worktree, one at a time inside its own run (so within `policy.timeouts.brief`), skipping those marked "new in this PR" and those that rewrite tracked files. It reports whether each can pass after a change within the expected files. `required` and `recommended` are criteria in prose, with ids `B1`, `B2` and on, the required ones first. The writer and the reviewer see them, and the reviewer reports each one as pass, fail or unverifiable. The driver decides (`briefOutcome` in `lib/checks.mjs`). A required criterion that does not pass, or a check that cannot pass, becomes a `brief-questions` block, unless a question of the reviewer names the criterion's id or quotes the command, and no brief is written. A recommended one that does not pass goes into the review notes. Each check and criterion logs a `gate-check` event with stage `brief` and `ahead`, the dependency heads the brief saw, instead of a SHA. A brief keeps the `gates.brief` it started with. Hand-written briefs are never checked.

## The delegate

Off unless `policy.delegate` is set (`{}` turns it on). When a PR blocks on a question of an allowed kind (`kinds`, default `brief-questions` and `needs-decision`, never `ci`, `environment`, `closed`, `gate` or `code-scanning`), a read-only delegate answers it from the plan, the brief, earlier answers and the code, or escalates. It escalates when the plan is silent or ambiguous, and on security, credentials, publishing, releases, weakened tests, code scanning, wider scope or spending. An answer reaches the agent like a `note`, prefixed as the delegate's. A question it takes notifies once, through its answer or escalation, and the `blocked` notice is skipped. Each question gets one run, a PR at most `maxPerPr` (2), at `effort` (`high`). The PR shows `running: delegate` meanwhile, and an escalation or a failed run hands the question back as `needs-you`, its sentence ending with the delegate's reason. A maintainer's `note` always wins. Its only power is text: it never approves, merges, retries, holds or releases.

## Lifecycle of one PR

Each PR has a stage and a status in the ledger. The stages run `brief` → `implement` → `pre-verify` → `verify` → `merge` → `merged`, and the status says what happens there: `running`, `waiting` or `needs-you`, with a code. `brief` (deps merged, or verified and not held, free slot) runs the brief writer and reviewer when there is no brief yet (with `gates.brief`, the reviewer runs the draft's commands and checks the project's criteria, and a check that cannot pass or a required criterion that does not pass stops on `brief-questions`) → `implement` (deps merged): agent opens PR, waits for CI, runs the ready commands of `gates.ready` in its self-check, reports READY with each one in `gates` → `pre-verify`: driver re-reads CI for that exact SHA, checks the rollout policy and reads new code scanning alerts, and with `gates.preVerify.scope` sends back files outside the scope that the READY report does not list in `deviations`, then, in a slot, runs the commands itself in the worktree at that head in this order: `gates.ready.required`, `gates.ready.recommended`, `gates.preVerify.required`, `gates.preVerify.recommended`. Only its own result counts. A failed required one sends the PR back and ends the run, and a failed recommended one only shows on the card, the PR page and in the verifier's prompt (each of these checks logs a `gate-check` event with its stage, `ready` for a ready command and `preVerify` for the rest, its level and result: pass, fail, or skip for code scanning that is off or unavailable) → `verify` (fresh read-only Opus session tries to refute READY against the brief's acceptance checklist and checks the criteria of `gates.verify` and the entries of its criteria catalog that apply to the PR, read from `origin/<base>` and fixed when it starts, where a required one that does not pass makes the verdict a FAIL, and after a FAIL re-checks the previous findings and the implementer's answers) → `merge`: gate (with the user's approval under `merge: human`) → `merged`.

Anything off sends the PR back to `implement` with a fix it owes, and the next tick resumes the implementer's own session as `implement · running: fix` with the reason: CI red, policy violation, new code scanning alerts, undeclared files out of scope, a failed required ready command (`ready check`, and the note says what the READY report claimed for it), a failed required pre-verify command (`pre-verify check`), verifier findings (a required `gates.verify` criterion that does not pass is one), gate verdict, rebase conflict, a maintainer's review. Verifier findings are numbered F1, F2 and on, and the implementer answers each one as fixed or disputed. A disputed finding the next verifier still finds open stops the PR on `verify · needs-you: dispute` instead of another fix round. A run that fails or dies without a report waits on the stage of its run, with a `no-report` fix on implement, and is resumed, but a fix run that fails, is stopped or is cut off by a crash keeps its reason and note for the next fix run, and a PR whose commands passed waits on `verify · waiting: slot` for its verifier. Caps from the manifest (`policy.attempts`) turn endless loops into `needs-you: attempts-exhausted`, and errors on one PR in five ticks in a row into `needs-you: errors`. An outage of GitHub or the network never counts toward those five. An agent that needs a human answer reports BLOCKED. The driver notifies at once and waits for `note`, unless the delegate takes the question. With `policy.delegate` on, the delegate may answer first.

- A run that did no work (stopped, rate-limited, or under $0.01 and a minute) gives its attempt back, at most five times. A run that a crash cut off counts the same way on the next start. Every failure backs off exponentially, up to 30 minutes. `retry` starts the refund count and the backoff streak over.
- Effort rises with attempts: each implement attempt after the first raises it one level, and so does each fix run from the third on. The verifier keeps its own.
- A spend, credit or billing limit on the Claude account, an account on hold or a failed login holds the whole rollout until `release --all`, with `by: driver` and the run's error as the reason. A hold already in place stays, a maintainer's included, and the notice still goes out.
- A hold sits beside the stage and status, in two scopes: `hold` on a PR, and the rollout's `hold` (no new runs, no merges). Each is `{ at, by, reason }`, with `by` the `maintainer` or the `driver`. A ledger an older driver wrote with `paused: true` becomes a maintainer's hold when the driver opens it. A red base is a rule of the gate.
- The fetch, the outside-dependency check and the base watch belong to no PR. A failure logs `fetch-failed`, `outside-deps-failed` or `watch-base-failed`, no PR counts it and the rest of the tick runs. A failed fetch skips merges for that tick. Five failures in a row of one step notify, and so do five failed ticks in a row (`tick-error`). A READY report GitHub could not read waits on `pre-verify · waiting: github` (`report-unchecked`) and is checked again on a later tick, with no agent run. It goes back as naming an unknown PR only when its PR read answers 404 while the repository still reads. Any other error, a 404 for both included, waits and counts as an error of the PR on each later tick, unless it is an outage.
- A GitHub or network outage (HTTP 5xx or 429, a rate limit, a DNS or connection failure, a timeout) counts against no PR and no driver-wide step, and fires no five-in-a-row notice. Each tick logs it once as `github-unavailable` and tries again. A start during an outage goes on, and logs it the same way. After 30 minutes in a row the driver notifies once, and once more when GitHub answers again (`github-back`).
- Agent timeouts and the stall watchdog count only awake time. A once-a-minute check that comes more than a minute late counts the gap as sleep, and the done events carry `seconds` (wall clock) and `awakeSeconds`. A gap between ticks more than a minute longer than `tickSeconds` logs `machine-slept`. For two minutes after it, every failed GitHub request or gh or git call is an outage. Any other error still counts.
- The driver reloads `manifest.yaml` every tick. An invalid edit is logged as `manifest-rejected` and the previous manifest stays. A missing `manifest.yaml` is rejected the same way, once.

## The merge gate (lib/judge.mjs, pure, tested)

Merges only when all hold: PR not held; PR open, not draft, base and branch as in the manifest, rollout label present, not the release PR; dependencies merged; verified for the current patch id, and under `merge: human` approved for it; no forbidden paths, no package version edits, a new changeset with at most `policy.maxBump`, no denylisted terms in the diff/PR/commits, one-line commits; branch contains the base (otherwise the driver rebases, and a conflict goes back to the implementer); mergeable; every check on the head SHA finished OK and every `requiredChecks` glob matched, where runs `repo.ignoredChecks` names count for nothing, on the head or on the base; the base branch itself is green, where a base commit with no run of a required check, no failed run and only `repo.baseQuietPaths` changes is skipped and the state comes from its parent, at most 20 in a row; without `--admin`, GitHub's own merge state allows it. A red base is checked right after the approval and the policy, as `base-red`, so a PR is not rebased onto it and red CI on its head is not sent back. A base whose CI still runs waits as `base-pending`, late in the order. The git facts are read with the global and system git config off and every diff option stated: names NUL-separated, added lines by hunk counts with `--text`, the patch id from the diff's bytes with full blob ids. A read that cannot be parsed is an error of that PR, never a fact. A verified PR whose patch id the gate no longer matches goes back to `pre-verify · waiting: ci` (`head-moved-reverify`, reason `not-verified`), without its verification and approval. A gate block is read again every tick, so a draft made ready or a label added moves on by itself, and a merge GitHub refuses waits for `retry`. A `cancelled` run counts only when its check has no other run on the commit, because it can come from another branch. Then `gh pr merge --squash [--admin] --match-head-commit <sha>`. New code scanning alerts at or above `repo.codeScanning.minSeverity` send the PR back or block it, and an analysis of an older commit waits. A block keeps the verification, and the claim check or the gate reads the alerts again every tick until they are dismissed. An implementer sure of a false positive reports BLOCKED `code-scanning`, which never goes to the delegate. The maintainer dismisses the alert on GitHub and runs `retry`, or sends a `note`. A PR merged on GitHub while the gate reads it waits, and the next sync records it. A PR merged on GitHub while one of its agents runs has that agent stopped in the same tick. A merge whose commit GitHub does not show yet logs `merge-unconfirmed` and stays verified until sync records it. One merge or rebase per tick. A red base after a rollout PR merges, by the driver or on GitHub, logs `base-red` and notifies once, and merges start again by themselves when the base is green.

The release PR ("chore: version packages") is never merged by the driver: merging it publishes. The driver reports it at the end; the user merges it.

## Guard rails for agents

- `sandbox.runtime`: `host`, the default, runs agents, `repo.install` and the ready and pre-verify commands as the user, so every bullet below is a seatbelt. `docker` runs each of them, and the driver's git in a clone once the clone is set up, in a container of its own (`rollout-<name>-<run>`). The container mounts only the PR's clone or brief preview, the skill directory read-only and a home. It runs with the user's uid and gid and no capabilities, gets only named variables (the bot's `GH_TOKEN`, `GH_REPO`, `ROLLOUT_ROLE`, the Claude token, the git identity, `sandbox.passEnv`) and reaches only the addresses of `sandbox.allowedDomains` over HTTPS, plus DNS. The limit: an agent holds the bot's token and the Claude token and can send either to an allowed host. `docs/security.html` has the details.
- Settings passed per agent: deny `gh pr merge/review/close`, `gh repo/release/secret/variable/workflow/ruleset`, publish and release commands, and `git push origin` to `main` or `repo.base`. Edit and Write are denied on the rollout and skill directories. Attribution is off. Tools that act in a later turn (`ScheduleWakeup`, the `Cron*` tools, `RemoteTrigger`, `Monitor`) are disallowed for every agent, because a headless run ends with its turn, and every prompt tells the agent to wait in the foreground.
- `hooks/guard-bash.mjs` (PreToolUse, Bash): its context is on the hook command (`--dir`, `--home`, `--name`, `--repo`, `--branch`), not in the agents' environment, and `ROLLOUT_ROLE` is the only `ROLLOUT_*` variable agents get. It is a seatbelt, the second layer under `sandbox.runtime: docker`: its rules act where its own reading puts the command word, subcommand and action, so a command it reads differently from the shell or the tool can get past them, such as `2>&1 $(echo git) push` or `git 2>/dev/null config …`, and `docs/security.html` lists the known limits. It lets pushes go only to the `--branch` value with an explicit refspec, whatever the base branch is called, no force except `--force-with-lease`, `gh api` GET only, no `--no-verify`, no hooksPath overrides, no `changeset version|publish|tag|pre`, run directly, through a package manager or by path. It refuses setting, unsetting or un-exporting `GH_TOKEN`, `GITHUB_TOKEN`, `GH_CONFIG_DIR`, `GH_REPO`, `GH_HOST` or a `ROLLOUT_*` variable in any form (`NAME=`, `NAME+=`, the shell builtins, `env -u`), and `env -i`, `env -S`, unknown `env` options and `exec -c`. `--repo`, `-R` and `gh api repos/…` must name the manifest's repository, the `--repo` value, lone `{owner}` or `{repo}` placeholders are refused, and without `--repo` any named repo is. It refuses `$ROLLOUT_…`, `$IFS`, brace expansion such as `{a,b}` or `{1..3}`, anything but a plain name right under the rollouts root, and a word built by expansion where it decides (the command word, `eval`, `sh -c`, git's global options, subcommand, `config`, `remote` and `push`, gh's subcommand and action and every `gh api` argument, the package managers' subcommand and the word after it, and the changesets CLI). A glob, zsh's `=cmd` and a `(…)` or `{…}` group count too in the flags before git's subcommand and the key of `-c`, git's subcommand, the arguments of `config` and `push` and the `remote` action, gh's subcommand and action, the flags, method and words of `gh api` but its endpoint, which may hold `?`, the package managers' subcommand and the changesets command. In the command word, and in the command of `eval` and `sh -c`, a glob and `=cmd` count, and a group counts at the start of the word or in a path, as in `/usr/bin/(g)it`, because quoted program text is full of calls such as `console.log(x)`. A `-c` override of a hook, credential or remote setting is refused anywhere in the command. A continued line with a `#` is read twice, joined and ended at its newline, because a comment ends at its newline. The names of the tools it reads count in any case, builtins and subcommands as written. For the verifier, the brief writers and the delegate it also refuses commits, pushes, branch switches and writes to GitHub, where its rule for `gh pr create|edit|comment|ready` looks for `pr` and the action side by side. It fails closed: its hook command ends with `|| exit 2`, so any exit other than 0 blocks, a hook command it cannot parse refuses every command, and it refuses lines (continuations joined) and simple commands over 16,384 characters and commands over 262,144. Claude Code runs a command whose hook timed out, so the hook's 30 s timeout is the one failure of the guard that lets a command run.
- `git-hooks/commit-msg` via each clone's `core.hooksPath`: one subject line, at most 72 characters, no body, no trailers. `git-hooks/pre-push`: only the PR branch, only the HTTPS push URL.
- `--permission-prompts none`: anything that would prompt is denied instead of hanging.
- Context: built-in tools as an allowlist per role (`--tools`: Bash, Read, WebFetch, WebSearch, TaskStop, plus Edit and Write for implement and fix), the project's settings only (`--setting-sources project`: `.claude/settings.json` and `CLAUDE.md` load, `.claude/settings.local.json`, `CLAUDE.local.md` and the user's settings do not), no MCP servers but the manifest's `mcpConfig` for implement and fix (`--strict-mcp-config`, and `docker` refuses `mcpConfig`), no skills (`--disable-slash-commands`) and no auto-memory (`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`). The guard and the permission rules come through `--settings`. The guard reads Bash only, so an MCP tool would get past it, and the read-only roles get no MCP server. Before every verifier and on a reset, the driver deletes untracked `.claude/settings.json`, `.claude/settings.local.json` and `CLAUDE.local.md` at the worktree root, because a global gitignore can hide them from `git status`, and logs `local-config-removed`. `repo.install` and the ready and pre-verify commands the driver runs get the read-only agents' environment (`ROLLOUT_ROLE=install` or `gate`, the bot's token when set, an empty npmrc, no npm tokens), because they run scripts from a worktree an agent may have written. The guard reads only the agents' tool calls, so it never sees what they run. Under `docker` they run in a container like the agents. The verifier, the brief writers and the delegate get a 5-minute prompt cache (`CLAUDE_CODE_PROMPT_CACHE_TTL=5m`) instead of a subscription's hour, which costs more per write. Implement and fix keep Claude Code's default, an hour on a subscription: they wait for CI, and a fix resumes the implementer's session.

## Starting a new rollout

1. Write the plan (`plan.md` in the rollout directory), the first of `briefing.sources`, in any language. Start each PR's entry with its id, in a heading (`### P1 feat: config loader`) or in bold at the start of a paragraph or a list item (``**P1 `feat/config-loader`** (deps)``, `- **P1 (config).** …`). The entry runs to the next heading of its level or higher, the next bold paragraph or the next item at its level. A source whose `tag` only one PR lists in `briefTags`, such as an addendum for that PR, is that PR's in full. The UI shows each PR its slices of the plan, and preflight warns about a PR without one. Agents always get the whole sources.
2. Create `$ROLLOUT_ROOT/<name>/manifest.yaml`. Copy the structure of `examples/manifest.yaml` in this skill: `rollout`, `model` (default `opus`, for every role but a PR's own `model.implement`), `claudeBin`, `mcpConfig`, `repo` (path, github, base, public, pathPrepend, install, requiredChecks, ignoredChecks, baseQuietPaths, agentToken, maintainers, merge, neverMerge, forbid, denylist, codeScanning, verify recipe), `briefing`, `policy` (concurrency, merge, approval, maxBump, attempts, timeouts, stallMinutes, ciStallMinutes, budgetUsd, tickSeconds, mergeDelaySeconds, feedbackQuietMinutes, delegate), `gates` (brief.runChecks, brief.required and brief.recommended, the reviewer's checks of a brief the driver writes, then ready.required and ready.recommended, the commands of the implementer's self-check that the driver runs again before the pre-verify commands, with an install first in ready.required, then preVerify.scope, preVerify.required, preVerify.recommended, then verify.required and verify.recommended, the criteria the verifier checks, and verify.criteriaFrom, a YAML catalog of more criteria in the repo, read from `origin/<base>`), `sandbox` (runtime, image, oauthTokenFile, allowedDomains, passEnv, memory, cpus, pidsLimit), and `prs` with `id, branch, title, brief, deps, priority, effort {implement, verify, brief}, model {implement}, changeset, smoke, viewer, scope, allowWorkflows, allowClaudeConfig, briefTags, extra, expect`. Every field with its default is in `docs/manifest.html`. No PR branch or title, `repo.base` or `repo.github` may name the rollout, because the guard refuses every agent command that does. Loading the manifest fails when one does.
3. Write one brief per PR in `briefs/<id>.md`, in English, self-contained: goal, background with file:line on the base branch, concrete changes, out of scope, expected files, changeset text, verification commands with expected numbers, an objectively checkable acceptance checklist, PR description skeleton. The agent sees only the brief, the repo and the protocol. Best made by one agent per PR plus an adversarial reviewer that checks every path and claim against the base branch.
4. Models: `model: { implement: sonnet }` moves a PR's implementer and its fixes to another model, for mechanical work. Its second implement attempt and third fix, the ones that raise the effort, go to the rollout's `model`, and the PR stays there, also after `retry`. The verifier, the brief writers and the delegate always run on the rollout's model. Every `*-start` event names the model asked for and every `*-done` event the one that ran, so costs and outcomes compare per model.
5. Efforts: `max` for subtle runtime or concurrency work, `xhigh` for public-API or cross-package changes, `high` for mechanical multi-file work, `medium` for docs. Give the verifier `xhigh` when the implementer has `max`. Each run's `--max-budget-usd` is `policy.budgetUsd` for its effort. There is no cap for the whole rollout.
6. `preflight --live`, then a first run with `--only` on one or two PRs and `--dry-run` (everything real except the merge), then real runs.

## Machine setup

- Node 24+, git, gh 2.40.0 or later and the repo's package manager. Preflight probes node, gh and the manager that `repo.install` and `repo.verify.common` start with, and warns below gh 2.40.0.
- `claude` 2.1.303 or later on PATH (with `repo.pathPrepend` first), or `claudeBin` in the manifest. Preflight warns below 2.1.303. Under the host runtime agents inherit the driver's environment, so they use the user's `claude` login or `ANTHROPIC_API_KEY`. They do not load the user's Claude Code settings, so an `apiKeyHelper` or `env` set there never reaches them, and preflight warns about both. When the first `claude` on PATH is a wrapper script, such as the shim cmux puts there, preflight warns: agents would run through it, with whatever it adds, and stop when it stops them. Set `claudeBin` to the real binary.
- `sandbox.runtime: docker` needs a Docker daemon that `docker` on PATH reaches (`DOCKER_HOST` and the current context pick it, and a Docker VM such as colima must share the clones and the skill directory), the image from `node $R sandbox build` (built again after claude updates), and `sandbox.oauthTokenFile` with a token from `claude setup-token` (chmod 600) or `ANTHROPIC_API_KEY` in `sandbox.passEnv`. It also needs `repo.agentToken` and refuses `mcpConfig`. Agents run the image's claude, not `claudeBin`. The image has npm and no pnpm.
- Notices go to the targets of `policy.notify`. The desktop is on by default, through `osascript` on macOS and `notify-send` on Linux, and `policy.notify.desktop: false` turns it off. `policy.notify.command` runs with `sh -c`, with the title in `$1` and `ROLLOUT_NOTIFY_TITLE` and the message in `$2` and `ROLLOUT_NOTIFY_MESSAGE`. `policy.notify.webhook` gets a JSON POST of `{ rollout, title, message, at }`. A failing target logs `notify-failed` once per target per driver run.
- For a long run on a Mac, plug in and keep the lid open. `caffeinate -is` keeps a Mac awake only on AC power, and closing the lid sleeps it anyway. On battery `run`, `preflight` and the UI's Start warn. Other platforms get no warning.
- `ROLLOUT_DIR` sets the default `--dir`. `ROLLOUT_ROOT` sets the default root for `ui`.
- `repo.public: false` marks a private repo. Its prompts drop the public-repository rules and keep the denylist.
- Accounts and GitHub side: `docs/accounts.html`. Threat model: `docs/security.html`.
