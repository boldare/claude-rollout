# rollout

A rollout is one plan shipped as several PRs. The orchestrator is a **process**, not a model: `bin/rollout.mjs run` ticks every minute, reads the truth from GitHub, starts headless agents (`claude -p`), checks the merge gate and merges. A model never drives the loop, so a stalled session cannot stall the rollout, and restarting the same command resumes from GitHub state plus the local ledger.

Everything lives in two places:

- this skill: its own directory, the installed copy (for example `~/.claude/skills/rollout/`), with the driver, prompts, schemas, guard hook, git hooks, docs and tests.
- one directory per rollout, outside any repo: `$ROLLOUT_ROOT/<name>/` (default `~/.rollouts`) with `manifest.yaml`, `briefs/<id>.md` (local only: they may name clients), `ledger.json`, `events.jsonl`, `heartbeat`, `driver.lock`, `driver.log`, `logs/`, `inbox/`. Its worktrees live next to it in `<name>.worktrees/`.

`R` below is `bin/rollout.mjs` in this skill's directory. The full manual for people is `docs/index.html` in the same directory.

## Install

The repository is the skill: `SKILL.md` sits at its root. Clone it into the skills directory and install its one dependency:

```sh
git clone https://github.com/grzehub/claude-rollout ~/.claude/skills/rollout
cd ~/.claude/skills/rollout && npm ci
```

A clone anywhere else works for the CLI alone. Never point the installed skill at a checkout someone develops in. The driver reads the prompts, schemas, guard and git hooks from its own directory on every agent run, so switching branches there changes a running rollout. To update, `stop` the driver, run `git pull && npm ci`, and `run` again.

A running driver watches `inbox/`, so commands apply within about a second instead of at the next tick. Without a driver they wait in the inbox for the next `run`. With `ROLLOUT_ROLE` set (inside an agent) only `status`, `card` and `help` work.

When the user asks "how is the rollout going", run `status`, read the cards of anything verified or blocked, and summarise: what is waiting for them (approvals, questions), what is running, what failed.

Before approving on the user's behalf: never. Approval is the user's decision; show the card and let them review on GitHub or run `approve`.

## Identity and approvals

- `repo.agentToken` points to a token file of a separate GitHub account (write role, no ruleset bypass). Agents get it as `GH_TOKEN` with an empty `GH_CONFIG_DIR`, so they open PRs and push as that account and cannot fall back to the maintainer's stored `gh` login. Worktrees push over HTTPS (`remote.origin.pushurl`, `gh auth git-credential`); the pre-push hook refuses any other URL, so the maintainer's SSH key is never used for pushes. The driver itself reads GitHub and merges with the maintainer's `gh` login.
- `policy.merge` (default `human`): `manual` (the driver verifies, gates, rebases and notifies "ready to merge"; the maintainer merges on GitHub and the driver carries on from the merge), `human` (the driver merges after the maintainer's approval) or `auto`. Approval counts in the gate only under `human`: under `manual` the maintainer's merge is the approval, and `auto` needs none.
- `policy.approval` (default `inbox`, which means `rollout approve`) or `github` with `repo.agentToken` and `repo.maintainers`: a PR from the agents' account counts as approved when a maintainer's latest review is APPROVED and was submitted after the current patch appeared, and no maintainer's latest review requests changes. Time, not the review's commit: GitHub moves a non-dismissed review's `commit_id` to new heads. Such PRs merge without `--admin` (`merge.admin: auto`). PRs a maintainer authored cannot be self-approved on GitHub, so they use `rollout approve` and the PR bypass.
- After an approval the driver waits `policy.mergeDelaySeconds` (120 s) before merging; `pause` in that window stops it. When GitHub's ruleset still blocks the merge, the gate waits instead of merging, and a refused merge is logged as `merge-refused`.
- Review comments by `repo.maintainers` (inline, review bodies and conversation) start a fix run once the maintainer has been quiet for `policy.feedbackQuietMinutes` (3). The driver replies in the threads as the agents' account, or as the maintainer without `repo.agentToken` (preflight warns when `repo.maintainers` is set). Its replies and summary comment end with a hidden `<!-- rollout-driver -->` line, and feedback collection skips comments ending with it. Comments by anyone else never reach an agent.

## Briefs written by the driver

A PR whose `brief` file does not exist gets one when its dependencies are merged (`briefing.sources` in the manifest: the plan plus design notes, `tag`ged per track and picked by the PR's `briefTags`). A source's `kind` is `markdown` or `transcript`, the last long assistant text of a Claude Code JSONL. A relative `path` resolves against the driver's working directory, so use absolute or `~` paths. A read-only writer drafts it on a worktree of the current base, a read-only reviewer checks every path, line and command against that code and returns the final text, and the driver writes `briefs/<id>.md` plus `<id>.review-notes.md`. Brief runs use `effort.brief` (default `xhigh`). Open product questions stop the PR as `blocked (brief-questions)`; `note <id> "<answers>"` re-runs the writer with the answers. The brief's expected files become the PR's scope when the manifest has none.

## Lifecycle of one PR

`pending` → (deps merged, free slot) `briefing` if there is no brief yet, then back to `pending` → `implementing` → agent opens PR, waits for CI, reports READY → `ready_claimed` → driver re-reads CI for that exact SHA and checks the rollout policy → `verifying` (fresh read-only Opus session tries to refute READY against the brief's acceptance checklist) → `verified` → gate (with the user's approval under `merge: human`) → `merged`.

Anything off sends the PR to `needs_fix`, and the next tick resumes the implementer's own session as `fixing` with the reason: CI red, policy violation, verifier findings, gate verdict, rebase conflict, a maintainer's review. A run that fails or dies without a report becomes `interrupted` and is resumed. Caps from the manifest (`policy.attempts`) turn endless loops into `escalated`, and so do five errors in a row on one PR. An agent that needs a human answer reports BLOCKED; the driver notifies and waits for `note`.

- A run that did no work (stopped, rate-limited, or under $0.01 and a minute) gives its attempt back, at most five times. Every failure backs off exponentially, up to 30 minutes.
- Effort rises with attempts: each implement attempt after the first raises it one level, and so does each fix run from the third on. The verifier keeps its own.
- A spend, credit or billing limit on the Claude account, an account on hold or a failed login pauses the whole rollout until `resume`.
- `held` is a flag on one PR, not a state. `paused` (no new runs, no merges) and `halted` (no merges, after a red base) apply to the whole rollout.
- The driver reloads `manifest.yaml` every tick. An invalid edit is logged as `manifest-rejected` and the previous manifest stays.

## The merge gate (lib/judge.mjs, pure, tested)

Merges only when all hold: rollout not halted and PR not held; PR open, not draft, base and branch as in the manifest, rollout label present, not the release PR; dependencies merged; verified for the current patch id, and under `merge: human` approved for it; no forbidden paths, no package version edits, a new changeset with at most `policy.maxBump`, no denylisted terms in the diff/PR/commits, one-line commits; branch contains the base (otherwise the driver rebases, and a conflict goes back to the implementer); mergeable; every check on the head SHA finished OK and every `requiredChecks` glob matched; the base branch itself is green; without `--admin`, GitHub's own merge state allows it. Then `gh pr merge --squash [--admin] --match-head-commit <sha>`. One merge or rebase per tick. A red base after a rollout PR merges, by the driver or on GitHub, halts the rollout.

The release PR ("chore: version packages") is never merged by the driver: merging it publishes. The driver reports it at the end; the user merges it.

## Guard rails for agents

- Settings passed per agent: deny `gh pr merge/review/close`, `gh repo/release/secret/variable/workflow/ruleset`, publish and release commands, and `git push origin` to `main` or `repo.base`. Edit and Write are denied on the rollout and skill directories. Attribution is off.
- `hooks/guard-bash.mjs` (PreToolUse, Bash): pushes only to `$ROLLOUT_BRANCH` with an explicit refspec, whatever the base branch is called, no force except `--force-with-lease`, `gh api` GET only, no `--no-verify`, no hooksPath overrides, no `changeset version|publish|tag|pre` in any form. The verifier and the brief writers cannot commit, push, switch branches or write to GitHub. It fails closed: an unreadable payload or an error of its own blocks with exit 2.
- `git-hooks/commit-msg` via per-worktree `core.hooksPath`: one subject line, at most 72 characters, no body, no trailers. `git-hooks/pre-push`: only the PR branch, only the HTTPS push URL.
- `--permission-prompts none`: anything that would prompt is denied instead of hanging.

## Starting a new rollout

1. Create `$ROLLOUT_ROOT/<name>/manifest.yaml`. Copy the structure of `examples/manifest.yaml` in this skill: `rollout`, `model` (default `opus`, for every role), `claudeBin`, `repo` (path, github, base, public, pathPrepend, install, requiredChecks, agentToken, maintainers, merge, neverMerge, forbid, denylist, verify recipe), `briefing`, `policy` (concurrency, merge, approval, maxBump, attempts, timeouts, stallMinutes, ciStallMinutes, budgetUsd, tickSeconds, mergeDelaySeconds, feedbackQuietMinutes), and `prs` with `id, branch, title, brief, deps, priority, effort {implement, verify, brief}, changeset, smoke, viewer, scope, allowWorkflows, briefTags, extra, expect`. Every field with its default is in `docs/manifest.html`.
2. Write one brief per PR in `briefs/<id>.md`, in English, self-contained: goal, background with file:line on the base branch, concrete changes, out of scope, expected files, changeset text, verification commands with expected numbers, an objectively checkable acceptance checklist, PR description skeleton. The agent sees only the brief, the repo and the protocol. Best made by one agent per PR plus an adversarial reviewer that checks every path and claim against the base branch.
3. Efforts: `max` for subtle runtime or concurrency work, `xhigh` for public-API or cross-package changes, `high` for mechanical multi-file work, `medium` for docs. Give the verifier `xhigh` when the implementer has `max`. Each run's `--max-budget-usd` is `policy.budgetUsd` for its effort. There is no cap for the whole rollout.
4. `preflight --live`, then a first run with `--only` on one or two PRs and `--dry-run` (everything real except the merge), then real runs.

## Machine setup

- Node 20+, git, gh and pnpm. Preflight probes pnpm too.
- `claude` on PATH (with `repo.pathPrepend` first), or `claudeBin` in the manifest. Agents inherit the driver's environment, so they use the user's `claude` login or `ANTHROPIC_API_KEY`.
- Notifications go through `osascript` on macOS and `notify-send` on Linux. Other platforms get none.
- `caffeinate` is optional and used only on macOS.
- `ROLLOUT_DIR` sets the default `--dir`. `ROLLOUT_ROOT` sets the default root for `ui`.
- `repo.public: false` marks a private repo. Its prompts drop the public-repository rules and keep the denylist.
- Accounts and GitHub side: `docs/accounts.html`. Threat model: `docs/security.html`.
