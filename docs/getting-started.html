Getting started

SKILL.md · examples/manifest.yaml

Install the skill, describe your plan as a manifest and run it on one PR as a dry run. The first real merge comes after that, when you trust what you saw.

Requirements #

Everything runs on your machine, as your OS user. rollout preflight checks most of this list before a first run.

Tool Why Preflight
Node 20+ Runs the driver, the CLI and the UI. CI tests Node 20 and 22. node --version must run
git Worktrees, fetches and rebases. git fetch origin in repo.path
gh Your login reads GitHub and merges. The bot's token opens PRs and pushes. gh auth status must pass
pnpm Preflight requires it for every repo, even one that does not use pnpm. pnpm --version must run
claude Every agent is a headless claude -p. It is found on PATH, with repo.pathPrepend first, or set claudeBin in the manifest. claude --version. Only --live proves the login.
osascript, notify-send Desktop notifications on macOS and Linux. Other platforms get none. not checked
caffeinate Optional, macOS only. Keeps the machine awake during a long run. not checked

You also need two GitHub accounts and a Claude login. Accounts explains both.

Install #

The repository is the skill. SKILL.md sits at its root, and Claude Code loads personal skills from ~/.claude/skills/<name>/SKILL.md. So one clone gives you both the CLI and the /rollout skill.

Recommended: clone into the skills directory

git clone https://github.com/grzehub/claude-rollout ~/.claude/skills/rollout
cd ~/.claude/skills/rollout
npm ci

R=~/.claude/skills/rollout/bin/rollout.mjs
node $R help

yaml is the only runtime dependency. Always call the CLI as node $R. The file is not executable, and npm ci puts no rollout command on your PATH. These docs write rollout <command> for short. An alias makes that literal: 

alias rollout="node ~/.claude/skills/rollout/bin/rollout.mjs"

CLI only

Clone it anywhere and run npm ci there. The driver finds its prompts, schemas, guard hook and git hooks next to its own code (HOME in lib/manifest.mjs), so the location does not matter. Claude Code just does not know the skill.

Why not a symlink to your dev checkout

The driver reads its prompts, report schemas, guard hook and git hooks from its own directory on every agent run (lib/prompts.mjs, lib/spawn.mjs, lib/settings.mjs, lib/worktree.mjs). When the skill is a symlink to the checkout you work in, switching branches there swaps them under a running rollout.

So keep the installed copy as a clone of its own, and develop in a second clone. CLAUDE.md makes the same point for agents that work on this repo.

Updating

Stop the driver, pull, and start it again. Implementer sessions resume where they stopped. A verifier or brief run starts over. 

node $R stop --dir ~/.rollouts/my-lib-1.2.0
cd ~/.claude/skills/rollout && git pull && npm ci
node $R run --dir ~/.rollouts/my-lib-1.2.0

Copying instead of cloning? Keep the executable bits of git-hooks/commit-msg and git-hooks/pre-push. Git skips a hook that is not executable, so the push and commit rules for agents would silently stop applying.

Your first rollout #

The example ships my-lib 1.2.0 in two PRs: P1 adds a config loader, P2 adds CLI flags on top of it.

  1. Set up the accounts

    A bot account with the Write role and its token, a ruleset on the base branch, squash merges, and a working claude login. Accounts walks through all of it.

  2. Create the rollout directory

    One directory per rollout, outside any repo. The driver keeps its state there.

    mkdir -p ~/.rollouts/my-lib-1.2.0/briefs

    The PR worktrees go next to it, in ~/.rollouts/my-lib-1.2.0.worktrees/. Briefs stay local on purpose: they may name clients.

  3. Write manifest.yaml

    The smallest useful manifest names the repo, its CI checks and the PRs:

    rollout: my-lib-1.2.0

repo:
  path: ~/code/my-lib
  github: my-org/my-lib
  requiredChecks: ['test*', 'lint']
  install: pnpm install --frozen-lockfile
  agentToken: ~/.config/rollout/agent-gh-token
  maintainers: [my-github-login]

policy:
  merge: human # the driver merges after your approval
  approval: github # approve the bot's PRs with a GitHub review

prs:
  - id: P1
    branch: feat/config-loader
    title: 'feat: config loader'
    brief: briefs/P1.md
    effort: { implement: xhigh, verify: xhigh }
    changeset: minor

  - id: P2
    branch: feat/cli-flags
    title: 'feat: cli flags'
    brief: briefs/P2.md
    deps: [P1]
    effort: { implement: high, verify: high }
    changeset: minor

    A repo without changesets uses changeset: none. examples/manifest.yaml shows every section, and Manifest describes every field and its default.

  4. Give every PR a brief

    Either write briefs/P1.md yourself, or let the driver write it. The agent sees only the brief, the repo and its protocol, so a brief must stand on its own. Write it in English, with:

    • the goal, and background with file:line references on the base branch
    • the concrete changes, and what is out of scope
    • the expected files and the changeset text
    • verification commands with the numbers you expect
    • an acceptance checklist that can be checked objectively
    • a skeleton of the PR description

    To have briefs written, point briefing.sources at your plan. Use an absolute or ~ path, because a relative one resolves against the directory you start the driver from. A read-only writer drafts the brief once the PR's dependencies are merged, and a read-only reviewer checks it against the code. Open questions stop the PR as blocked until you answer them with rollout note.

    The brief writer's prompt assumes the plan is written in Polish, with a "Decyzje" section for its decisions.

  5. Run preflight, then the live preflight 
    node $R preflight --dir ~/.rollouts/my-lib-1.2.0
node $R preflight --dir ~/.rollouts/my-lib-1.2.0 --live

    The first checks your tools, both GitHub identities and the repository settings. --live also starts a real headless agent with a small model and makes sure the guard refuses a merge, a push to main, a publish and a merge through the API. It is also the only check that proves your Claude login works.

  6. Do a dry run on one PR, in your own terminal 
    caffeinate -is node $R run --dir ~/.rollouts/my-lib-1.2.0 --only P1 --dry-run

    The driver runs for hours in the foreground, so start it in a terminal of your own, never inside a Claude Code session's Bash. caffeinate -is is optional and macOS only. Ctrl C stops the driver and its agents, and the same command resumes them.

  7. Watch it 
    node $R ui # another terminal: opens the web UI
node $R status --dir ~/.rollouts/my-lib-1.2.0
node $R card P1 --dir ~/.rollouts/my-lib-1.2.0

    Web UI shows every rollout under ~/.rollouts live. status prints a similar table in the terminal, and card shows what you need to approve one PR.

  8. Answer and approve

    A PR that needs an answer turns blocked, and you get a notification. A PR that passed the verifier turns verified. Read its card, then answer or approve: 

    node $R note P1 "Keep the old flag as an alias." --dir ~/.rollouts/my-lib-1.2.0
node $R approve P1 --dir ~/.rollouts/my-lib-1.2.0

    With approval: github, you approve the bot's PRs with a review on GitHub. approve is for a PR you authored yourself, because GitHub does not let you approve your own PR.

    The driver merges policy.mergeDelaySeconds (120 s) after the approval, and rollout pause in that window stops it. In this dry run you get a "would merge" notification instead.

  9. Go for real 
    node $R run --dir ~/.rollouts/my-lib-1.2.0

    Without --only and --dry-run, the driver works through every PR. It merges at most one PR per tick. A PR waits for its dependencies, and a higher priority goes first.

  10. Merge the release PR yourself

    When every PR is merged, the driver reports the release PR ("chore: version packages") and exits. It never merges that one, because merging it publishes. Review it and merge it on GitHub.

What a dry run does #

Everything is real except the merge. Agents run and cost money, branches are pushed, PRs are opened, CI runs, and the driver rebases and force-pushes branches. Only the merge becomes a would-merge event and a notification.

  • Under policy.merge: manual the driver never merges anyway, so --dry-run changes nothing there.
  • With --only, a PR whose dependency is outside the run waits for it. The dependency counts as merged once GitHub shows its branch merged into the base with the rollout's label.
  • The Start button in the UI offers a dry run, but not --only.

From Claude Code #

With the skill installed, ask Claude Code about a rollout in plain words, or type /rollout. "How is the rollout going?" makes it run status, read the cards of verified and blocked PRs, and tell you what waits for you, what runs and what failed.

  • It can queue commands for you, such as a note, a retry, a hold or a pause.
  • It never approves on your behalf. It shows the card, and you review on GitHub or run approve.
  • It does not start run or ui in its own Bash, because both run until you stop them. You start them in your terminal.
  • Agents inside a rollout cannot drive it. With ROLLOUT_ROLE set, only status, card and help work.
