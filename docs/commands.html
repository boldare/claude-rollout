Commands

bin/rollout.mjs

Everything goes through one script, bin/rollout.mjs. Run it with node and point it at a rollout directory. On this page $R is the path to that script. 

R=~/.claude/skills/rollout/bin/rollout.mjs
node $R status --dir ~/.rollouts/my-lib-1.2.0

Every command except ui and help loads the manifest of --dir first and stops when it does not validate. Commands that take a PR id refuse an unknown one and print the known ids.

At a glance #

command what it does in the UI
run Starts the driver in the foreground. Start button
stop Stops the driver and its agents. rollout header
status The PR table, the driver's heartbeat and recent events. board
card The approval card of one PR. PR page
ui Serves the web UI over every rollout under a root. –
approve Approves a verified PR for the gate. CLI only
note Answers an agent or asks for a change. PR page
retry Gives a PR fresh attempts. PR page
hold, release Holds one PR, or lifts the hold. PR page
pause, resume Stops new work and merges for the whole rollout, or lets them go on. rollout header
unhalt Clears a halt after a red base branch. rollout header
preflight Checks tools, logins, the repository and the guard. CLI only
help Prints the usage. CLI only

Run #

run #

node $R run --dir D [--only P1,P2] [--dry-run]

Starts the driver in the foreground. It runs for hours, so start it in a terminal of your own, never inside a Claude session's Bash. On macOS, caffeinate -is node $R run … keeps the machine awake.

  • It takes driver.lock. A second driver for the same directory refuses to start and names the pid of the first. A lock left by a dead process, or one without a real pid, is cleared.
  • On start, runs that were in progress get their attempt back and become interrupted, or pending for a brief. Then it fetches origin, creates the label rollout:<name> and turns on per-worktree git config.
  • It ticks every policy.tickSeconds (60 s), and a new command in the inbox wakes it sooner. What one tick does is on How it works.
  • When every PR of the run has merged, it reports the release PR for you to merge and exits.
  • Ctrl-C, SIGTERM or SIGHUP stops the agents, waits up to 15 s for them, saves and exits. A second signal exits at once. The next run resumes the implementers' sessions. Verifications and briefs start over.
--only P1,P2
Runs only these PRs. The rest of the manifest still counts for dependencies. A dependency outside the run counts as merged once GitHub shows its branch merged into the base with the rollout label. Until then the PR waits, and the driver says so when it starts.
--dry-run
Everything is real except the merge: agents, pushes, PRs, CI and the driver's own rebases. Where it would merge, it logs would-merge and notifies you. Under merge: manual it changes nothing, because the driver never merges then.

In the UI, the Start button starts the driver detached, with its output in driver.log, under caffeinate -is on macOS when it exists. It offers a dry run but not --only.

stop #

node $R stop --dir D

Sends SIGTERM to the pid in driver.lock and waits up to 30 s for the lock to go. It signals only a live pid above 1, with the same check as the UI's Stop. The driver stops its agents with SIGTERM, then SIGKILL after 5 s. The next run resumes the implementers' sessions, and verifications and briefs start over. Without a driver it prints no driver is running, and a lock with pid 0 or -1 counts as no driver. Any other refusal prints the reason and exits 1.

Watch #

status and card only read the rollout directory. They never call GitHub, so they work for a stopped rollout too. Agents may run both.

status #

node $R status --dir D

Prints, from top to bottom:

  • The driver: running with its pid, heartbeat age and note, or NOT RUNNING with the time of its last heartbeat.
  • PAUSED and HALTED lines when they apply.
  • One row per PR: id, state, PR number, head, CI or gate info, attempts as implement/fix/verify, and cost.
  • The last 8 events.

Before the first run there is no ledger yet, and it says so. The UI's board shows the same table with more columns.

card #

node $R card P1 --dir D

Everything you need before you approve one PR:

  • Title, branch, state, PR link and cost, and since when it is held.
  • The verified head and patch id, the approved head, the author and how approval works for it.
  • The gate's last action and its reasons.
  • The brief's path, and the reviewer's notes when the driver wrote it.
  • For a blocked PR, the agent's question and evidence.
  • With policy.delegate on, or after it answered, the delegate's runs and every answer or escalation with its plan references.
  • The implementer's summary, its deviations, and expected against observed results.
  • Changed CI and workflow files, to review before approving, and files outside the scope.
  • The verifier's verdict, checklist, blocking and non-blocking findings.
  • For a verified PR, how to approve it: the GitHub link or the approve command. Under merge: manual and merge: auto the card says no approval is needed and what happens instead.

In the UI, the same facts are on the PR page, across its overview and verifier tabs.

ui #

node $R ui [--root ROOT] [--port N] [--no-open] [--read-only]
  • Serves the web UI over every rollout under the root. It needs no --dir and no manifest.
  • Listens on 127.0.0.1 only, on a random port unless --port is given.
  • Prints a URL with a token in its fragment and, on macOS and Linux, opens it in the browser unless --no-open.
  • --read-only disables every control.
  • Runs until Ctrl-C, so start it in a terminal of your own.
  • Agents cannot run it, because the printed URL carries the token.

What it shows and how it works: Web UI.

Decide #

approve #

node $R approve P1 --dir D

Approves the verified patch of a PR. The CLI refuses it before it posts anything when this command does not count for the PR:

  • Under merge: manual. You merge on GitHub once the driver says the PR is ready.
  • Under merge: auto. The driver merges once the gate passes, and hold stops it.
  • For a PR the bot opened under approval: github. A maintainer approves it with a normal review on GitHub.

The refusal says what to do instead. The CLI also refuses a PR that is not verified, and otherwise posts the exact head and patch id from the ledger. The driver accepts the approval only when all of this still holds:

  • The policy and the PR's author still let this command count.
  • The PR is still verified, with that same head and patch id.
  • The approval was posted after the verification finished.
  • No agent is working on the PR.

A rejected approval shows up as approval-rejected in the events, with a notification.

The approval counts under merge: human only. The driver merges policy.mergeDelaySeconds (120 s) after it accepts the approval, unless you pause in that window. It notifies you when it accepts, and the CLI's reply names the delay.

The UI has no approve button, on purpose: approval stays a GitHub review or this command.

note #

node $R note P1 "Keep the old flag as an alias." --dir D

Sends a message from you to the PR's agents. The words after the id are joined, so the quotes are optional. What happens depends on the PR's state:

state what the note does
blocked by brief questions Your answer is kept with its questions until the brief is written. The PR returns to pending with its brief attempt back, and the brief writer runs again with every answer so far.
pending, or an agent other than the delegate is running Queued. The next brief, implement or fix prompt gets it.
merged Rejected.
no brief file and no GitHub PR For example a PR that escalated because no brief could be written. The note becomes an answer for the brief writer, as for brief questions.
verified ready_claimed The verification is dropped and the PR goes to needs_fix, with the reason "request from the maintainer".
needs_fix Queued for the fix run. The reason the PR waits with, and its details, stay.
any other state The PR goes to needs_fix, with the reason "answer from the maintainer". This is how you answer an agent that reported BLOCKED.

For a verified or ready_claimed PR, a needs_fix PR and any other state, the fix attempts are capped at one below the limit, so at least one more fix run is allowed. The fix run resumes the implementer's own session when there is one. In the UI: Note.

A note always wins over the delegate. Sent while the delegate runs, it applies at once, and the delegate's result is dropped (delegate-dropped). Sent after a delegate answer, it still reaches the agent, queued or as a new fix reason.

retry #

node $R retry P1 --dir D
  • Resets all four attempt counters (implement, fix, verify and brief), the error count, the backoff, the refund count, the failure streak and the delegate's run count.
  • A PR with a GitHub PR or an agent session becomes interrupted, and the next tick resumes it. That is a new verification when a claim waits for one, else a fix run.
  • Any other PR goes back to pending.
  • It is rejected for a merged PR and while an agent works on the PR. It does not clear a hold.

The UI offers Retry for escalated, blocked and interrupted PRs.

Control #

hold #

node $R hold P1 --dir D

Holds one PR: no new runs, rebases, ready notices or merges for it. A running agent finishes its step. The driver still syncs the PR with GitHub and collects review comments. It rejects a merged PR and one already held. In the UI: Hold.

release #

node $R release P1 --dir D

Lifts the hold. It rejects a PR that is not held. In the UI: Release.

pause #

node $R pause --dir D

Stops new runs and merges for the whole rollout. Running agents finish their step, and the driver keeps syncing with GitHub. It also stops a merge that waits out mergeDelaySeconds. In the UI: Pause.

resume #

node $R resume --dir D

Lifts the pause. The driver pauses itself when an agent run fails on an account problem, such as a spend limit, the credit balance or billing, and waits for this command. In the UI: Resume.

unhalt #

node $R unhalt --dir D

The driver halts when the base branch turns red after a rollout PR merges, by the driver or by you on GitHub. A halted rollout merges nothing, while agents keep working. Fix the base, then unhalt. It clears the halt and marks the last merge as acknowledged, so the same red commit does not halt the rollout again. In the UI: Unhalt.

Set up #

preflight #

node $R preflight --dir D [--live]

Checks the machine, your logins and the repository before a run. It prints an ok or FAIL line for most checks and a warn line per warning, and ends with preflight ok or preflight FAILED and the list, with exit code 1.

check fails or warns when
manifest It does not validate, or a brief is missing and there are no briefing sources. Nothing else runs then.
claude --version The binary does not run. Put it on PATH or in repo.pathPrepend, or set claudeBin.
node, package manager Either is missing. The manager is the first word of repo.install or of a repo.verify.common step, when it is npm, pnpm, yarn or bun. npx, pnpx and bunx count as their manager.
gh auth status Your own gh login is missing. The driver reads PRs, checks and reviews and merges with it.
git fetch origin repo.path is wrong or you cannot fetch.
origin Its owner and name must equal repo.github, case aside, so my-org/my-lib-next never passes for my-org/my-lib. The host must be github.com. An SSH host alias passes when ssh -G resolves it to github.com. HTTPS hosts are never resolved.
repository settings Fails when squash merges are disabled under merge.method: squash, when merge.admin is not false (the default auto counts) and you are not an admin, when a public repo is marked public: false, or when gh cannot read the repo. Warns when the squash default is not the PR title with a blank message, and when a private repo is marked public: true.
agent identity Fails when the token's login is a maintainer or its permission is not exactly write, when agents could fall back to a stored gh login, or when the token file is missing. Warns when the token lacks the workflow scope, and when there is no repo.agentToken at all. Without it, warns again when repo.maintainers is set, because comments agents post under your login count as your review feedback.
policy.merge Warns for auto: the driver merges without asking.
guard hook Feeding gh pr merge 1 --admin to the Bash guard does not end with exit code 2, or feeding it echo allowed does not end with exit code 0.
--live Starts a real headless claude -p (haiku, low effort) with the implementer's settings in a scratch directory. The guard must refuse a gh pr merge, a push to main, a pnpm publish and a gh api -X PUT merge, and echo allowed must run. A command that never ran fails too, so a Claude login or quota problem shows up here.

Preflight does not check rulesets, CODEOWNERS or code scanning, that requiredChecks name real jobs, that you are in repo.maintainers, or that repo.install works. Accounts covers those.

help #

node $R help

Prints the usage from the comment at the top of bin/rollout.mjs. So does node $R with no command. It needs no manifest.

Flags #

One parser serves every command, so every command accepts every flag and ignores the ones it does not use. An unknown flag or a missing value prints the error and the usage, and exits 1.

flag default used by meaning
--dir D $ROLLOUT_DIR, else the current directory all but ui and help The rollout directory, the one that holds manifest.yaml. A leading ~ expands.
--only A,B every PR run The PRs this run drives, comma separated. Every command checks the ids against the manifest.
--dry-run off run Everything real except the merge.
--live off preflight Also proves the guard in a real headless agent.
--root ROOT $ROLLOUT_ROOT, else ~/.rollouts ui The directory whose rollouts the UI lists: every subdirectory with a manifest.yaml.
--port N random ui A port from 0 to 65535. 0 picks a free one.
--no-open off ui Prints the URL without opening the browser.
--read-only off ui Disables every control. The server refuses every command.

Environment #

variable set by meaning
ROLLOUT_DIR you The default for --dir.
ROLLOUT_ROOT you The default root for ui. An empty value counts as unset.
ROLLOUT_ROLE the driver, for agents The agent's role. While it is set, the CLI refuses every command but status, card and help.
ROLLOUT_ID, ROLLOUT_BRANCH, ROLLOUT_NAME, ROLLOUT_HOME the driver, for agents The PR, its branch (empty for the verifier, brief and delegate roles), the rollout and the skill's directory. The Bash guard reads them. Agents also get ROLLOUT_DIR, so status and card work for them without flags.
GH_TOKEN, GH_CONFIG_DIR the driver, for agents The bot's token and an empty gh config directory, when repo.agentToken is set.
PATH the driver repo.pathPrepend goes first for the driver's own commands and for every agent. CLAUDECODE and CLAUDE_CODE_ENTRYPOINT are removed, so a driver started inside a Claude Code session does not make its agents look nested.

How commands reach the driver #

approve, note, retry, hold, release, pause, resume and unhalt never write the ledger. Each writes one small JSON file into inbox/, first under a dot-prefixed name and then renamed, so the driver never reads half a command. The CLI prints a short confirmation and returns.

  • A running driver watches the inbox and applies a command within about a second. A burst of commands becomes one tick.
  • Without a driver, the files wait and apply when the next run starts.
  • Each command applies on its own. One that is not a JSON object, names no PR or a PR the manifest no longer has, or fails while it applies shows up as command-rejected in events.jsonl, with the reason. A refused approval shows up as approval-rejected. The rest of the batch still applies.
  • Entries that are not files are skipped. A file the driver cannot delete is rejected instead of applied, on every tick until someone deletes it.

stop and the UI's Start are different: stop signals the driver's process and Start launches one. The UI writes the same inbox files as the CLI for everything else.
