Commands

bin/rollout.mjs

Everything goes through one script, bin/rollout.mjs. Run it with node and point it at a rollout directory. On this page $R is the path to that script. 

R=~/.claude/skills/rollout/bin/rollout.mjs
node $R status --dir ~/.rollouts/my-lib-1.2.0

Every command except ui and help loads the manifest of --dir first and stops when it does not validate. Commands that take a PR id refuse an unknown one and print the known ids.

At a glance #

command what it does in the UI
run Starts the driver in the foreground. Start button
stop Stops the driver and its agents. Rollout header
status The PR table, the driver's heartbeat and recent events. board
card The approval card of one PR. PR page
ui Serves the web UI over every rollout under a root. –
approve Approves a verified PR for the gate. CLI only
note Answers an agent or asks for a change. PR page
retry Gives a PR fresh attempts. PR page
hold, release Holds the PRs you name or the whole rollout, or lifts the hold. PR page Rollout header
preflight Checks tools, logins, the repository and the guard. CLI only
sandbox build Builds the agents' image for the Docker runtime. CLI only
help Prints the usage. CLI only

Run #

run #

node $R run --dir D [--only P1,P2] [--dry-run]

Starts the driver in the foreground. It runs for hours, so start it in a terminal of your own, never inside a Claude session's Bash. On macOS, caffeinate -is node $R run … keeps the machine awake, but only on AC power with the lid open. run warns when the Mac is on battery. Running for hours on a laptop has more.

  • Its first line is the runtime: runtime host, or runtime docker, image <tag>. Without sandbox.image the tag needs the version claude --version prints, and when it prints none, run stops there. The driver-start event records the runtime and the image too.
  • It takes driver.lock. A second driver for the same directory refuses to start and names the pid of the first. A lock left by a dead process, or one without a real pid, is cleared.
  • On start, runs that were in progress get their attempt back and become interrupted, or pending for a brief. Then it fetches origin and creates the label rollout:<name>.
  • It ticks every policy.tickSeconds (60 s), and a new command in the inbox wakes it sooner. What one tick does is on How it works.
  • When every PR of the run has merged, it reports the release PR for you to merge and exits.
  • Ctrl-C, SIGTERM or SIGHUP stops the agents and any ready or pre-verify commands, waits up to 15 s for them, saves and exits. A second signal exits at once. The next run resumes the implementers' sessions. Verifications, briefs and ready and pre-verify commands start over.
--only P1,P2
Runs only these PRs. The rest of the manifest still counts for dependencies. A dependency outside the run counts as merged once GitHub shows its branch merged into the base with the rollout label. Until then the PR waits, and the driver says so when it starts.
--dry-run
Everything is real except the merge: agents, pushes, PRs, CI and the driver's own rebases. Where it would merge, it logs would-merge and notifies you. Under merge: manual it changes nothing, because the driver never merges then.

In the UI, the Start button starts the driver detached, with its output in driver.log, under caffeinate -is on macOS when it exists. It offers a dry run but not --only. On battery its notice warns that caffeinate cannot keep the Mac awake.

stop #

node $R stop --dir D

Sends SIGTERM to the pid in driver.lock and waits up to 30 s for the lock to go. It signals only a live pid above 1, with the same check as the UI's Stop. The driver stops its agents and any ready or pre-verify commands with SIGTERM, then SIGKILL after 5 s. The next run resumes the implementers' sessions, and verifications, briefs and ready and pre-verify commands start over. Without a driver it prints no driver is running, and a lock with pid 0 or -1 counts as no driver. Any other refusal prints the reason and exits 1.

Watch #

status and card only read the rollout directory. They never call GitHub, so they work for a stopped rollout too. Agents may run both, but under the Docker runtime a container does not mount the rollout directory, so there they fail.

status #

node $R status --dir D

Prints, from top to bottom:

  • The driver: running with its pid, heartbeat age and note, or NOT RUNNING with the time of its last heartbeat.
  • The runtime of the manifest: runtime host, or runtime docker, image <tag>. The image is sandbox.image, else the one the last driver-start event records, else default. It never runs claude to find it.
  • A HELD line when the rollout is held: since when, by whom (maintainer or driver) and the reason when the hold has one.
  • One row per PR: id, state, PR number, head, CI or gate info, attempts as implement/fix/verify, and cost.
  • The last 8 events.

Before the first run there is no ledger yet, and it says so. The UI's board shows the same table with more columns.

card #

node $R card P1 --dir D

Everything you need before you approve one PR:

  • Title, branch, state, PR link and cost, and since when and by whom it is held.
  • The verified head and patch id, the approved head, the author and how approval works for it.
  • The gate's last action and its reasons.
  • The brief's path, and the reviewer's notes when the driver wrote it.
  • For a blocked PR, the agent's question and evidence.
  • With policy.delegate on, or after it answered, the delegate's runs and every answer or escalation with its plan references.
  • The implementer's summary, its deviations, and expected against observed results.
  • Changed CI and workflow files, to review before approving, and files outside the scope.
  • The verifier's verdict, checklist, blocking and non-blocking findings. With project criteria, each one with its id, level, text and result, and the evidence of one that did not pass. A PASS with a required criterion that did not pass shows as FAIL, with the criterion among the blocking findings. After a FAIL, each previous finding it re-checked, with its status, the implementer's answer and the evidence.
  • With ready or pre-verify commands, the driver's own results for the claimed head, under commands the driver ran at <sha>: each command with its result, stage, level and summary, and the last lines of output of a failed one.
  • For a verified PR, how to approve it: the GitHub link or the approve command. Under merge: manual and merge: auto the card says no approval is needed and what happens instead.

In the UI, most of these facts are on the PR page, across its overview, verifier and brief tabs. The patch id, the author and the implementer's summary, deviations and expected-vs-observed are only on the card.

ui #

node $R ui [--root ROOT] [--port N] [--no-open] [--read-only]
  • Serves the web UI over every rollout under the root. It needs no --dir and no manifest.
  • Listens on 127.0.0.1 only, on a random port unless --port is given.
  • Prints a URL with a token in its fragment and, on macOS and Linux, opens it in the browser unless --no-open.
  • --read-only disables every control.
  • Runs until Ctrl-C, so start it in a terminal of your own.
  • Agents cannot run it, because the printed URL carries the token.

What it shows and how it works: Web UI.

Decide #

approve #

node $R approve P1 --dir D

Approves the verified patch of a PR. The CLI refuses it before it posts anything when this command does not count for the PR:

  • Under merge: manual. You merge on GitHub once the driver says the PR is ready.
  • Under merge: auto. The driver merges once the gate passes, and hold stops it.
  • For a PR the bot opened under approval: github. A maintainer approves it with a normal review on GitHub.

The refusal says what to do instead. The CLI also refuses a PR that is not verified, and otherwise posts the exact head and patch id from the ledger. The driver accepts the approval only when all of this still holds:

  • The policy and the PR's author still let this command count.
  • The PR is still verified, with that same head and patch id.
  • The approval was posted after the verification finished.
  • No agent is working on the PR.

A rejected approval shows up as approval-rejected in the events, with a notification.

The approval counts under merge: human only. The driver merges policy.mergeDelaySeconds (120 s) after it accepts the approval, unless you hold the PR in that window (rollout hold P1). It notifies you when it accepts, and the CLI's reply names the delay.

The UI has no approve button, on purpose: approval stays a GitHub review or this command.

note #

node $R note P1 "Keep the old flag as an alias." --dir D

Sends a message from you to the PR's agents. The words after the id are joined, so the quotes are optional. What happens depends on the PR's state:

state what the note does
blocked by brief questions Your answer is kept with its questions until the brief is written. The PR returns to pending with its brief attempt back, and the brief writer runs again with every answer so far.
pending, or an agent other than the delegate is running Queued. The next brief, implement or fix prompt gets it. A note queued while a verifier runs sends the PR to a fix run before the next verification.
merged Rejected.
no brief file and no GitHub PR For example a PR that escalated because no brief could be written. The note becomes an answer for the brief writer, as for brief questions.
verified ready_claimed The verification is dropped and the PR goes to needs_fix, with the reason "request from the maintainer".
needs_fix Queued for the fix run. The reason the PR waits with, and its details, stay.
escalated over a disputed finding The PR goes to needs_fix with the reason "verifier findings" and the findings, and the note is queued for that fix run. It is recorded as your decision on the dispute, so the next verifier sees it.
any other state The PR goes to needs_fix, with the reason "answer from the maintainer", and loses any verification it still had. This is how you answer an agent that reported BLOCKED.

For a verified or ready_claimed PR, a needs_fix PR, a PR escalated over a disputed finding and any other state, the fix attempts are capped at one below the limit, so at least one more fix run is allowed. The fix run resumes the implementer's own session when there is one. In the UI: Note, or Answer for a blocked PR.

A note always wins over the delegate. Sent while the delegate runs, it applies at once, and the delegate's result is dropped (delegate-dropped). Sent after a delegate answer, it still reaches the agent, queued or as a new fix reason.

The driver records every note and delegate answer that applies, the last 20 of them. The verifier, and an implementer that starts a new session, get them all after the brief, oldest first. A decision wins over the brief.

retry #

node $R retry P1 --dir D
  • Resets all four attempt counters (implement, fix, verify and brief), the error count, the backoff, the refund count, the failure streak and the delegate's run count.
  • A PR escalated over a disputed finding goes to needs_fix, and a fix run gets the findings again.
  • A PR whose verification still holds goes back to verified. The next tick syncs its head with GitHub, then the gate looks again.
  • A verification for an older head is dropped, and the PR goes to ready_claimed. The driver checks the claim again, then verifies it.
  • A READY report that waits to be checked is claimed again on the next tick, with no agent run.
  • Otherwise a PR with a GitHub PR or an agent session becomes interrupted, and the next tick resumes it. That is a new verification when a claim waits for one, else a fix run.
  • Any other PR goes back to pending.
  • It is rejected for a merged PR and while an agent works on the PR. It does not clear a hold.

The UI offers Retry for escalated, blocked and interrupted PRs.

Control #

hold #

node $R hold P1 P2 --dir D
node $R hold --all --dir D

Holds the PRs you name, or the whole rollout with --all. One command holds several PRs. Each hold records who set it and since when, and status and card print both.

  • A held PR gets no new runs, rebases, ready notices or merges. A running agent finishes its step. The driver still syncs the PR with GitHub and collects review comments. A PR that depends on the held one gets no brief until release or the merge, and a brief already running finishes. This also stops a merge that waits out mergeDelaySeconds.
  • A held rollout starts no new runs and merges nothing. Running agents finish their step, and the driver keeps syncing with GitHub.
  • The driver rejects a merged PR and one already held. It rejects hold --all on a rollout already held, and the reason names who held it and since when. The other PRs of the same command still apply.
  • The driver holds the rollout itself when an agent run fails on an account problem, such as a spend limit, the credit balance or billing. That hold names driver and the run's error. A hold already in place stays as it is, and you get the notice anyway.

In the UI: Hold on a PR page and Hold all in the rollout header.

release #

node $R release P1 P2 --dir D
node $R release --all --dir D

Lifts the hold of the PRs you name, or the rollout's hold with --all. The two holds stay apart. release --all never lifts the hold of a PR, and release P1 never lifts the rollout's. The released event of release --all lists the PRs still held on their own in stillHeld.

The driver rejects a PR that is not held, and release --all on a rollout that is not held. While the rollout is held, the rejection of a PR says so and names release --all. release --all also lifts the driver's own hold after an account limit. In the UI: Release and Release all.

Set up #

preflight #

node $R preflight --dir D [--live]

Checks the machine, your logins and the repository before a run. It prints an ok or FAIL line for most checks, an info line for facts that are neither a problem nor a warning, and a warn line per warning. It ends with preflight ok or preflight FAILED and the list, with exit code 1.

check fails or warns when
manifest It does not validate, or a brief is missing and there are no briefing sources. Nothing else runs then.
plan sections Warns when a PR of the run has no section in the briefing sources it gets, so the UI cannot show its slice of the plan. The agents still get every source in full. See Plan for what counts as a section.
claude --version The binary does not run. Put it on PATH or in repo.pathPrepend, or set claudeBin.
claude wrapper Warns when the first claude on PATH is a wrapper script, a shebang script that is not node, such as the shim cmux puts there. It names the binary behind it, for claudeBin. A claudeBin with a path is never checked.
user settings Warns when your Claude Code user settings (settings.json in CLAUDE_CONFIG_DIR, or ~/.claude) set apiKeyHelper or env. Agents start with --setting-sources project, so they get neither. It names the env variables, never their values. Put what agents need in the environment that starts the driver. A file that is missing or not valid JSON prints nothing.
node, package manager Either is missing. The manager is the first word of repo.install or of a repo.verify.common step, when it is npm, pnpm, yarn or bun. npx, pnpx and bunx count as their manager.
gh --version The binary does not run. Put it on PATH or in repo.pathPrepend.
claude and gh versions The versions on your machine. Warns when claude is older than 2.1.303 or gh older than 2.40.0, the versions the driver was verified on, or when either prints no version. It never fails.
runtime Under the host runtime, one warning: agents, installs and gate commands run as you. Under sandbox.runtime: docker it fails when there is no docker client on PATH, when docker version gets no answer from the daemon, when the image is missing (build it with sandbox build), when claude or gh in the image is older than the verified versions or prints none, when sandbox.oauthTokenFile is empty, or when sandbox.passEnv names ANTHROPIC_API_KEY and it is not set. It warns when the image's claude differs from yours. An info line says that claudeBin and repo.pathPrepend apply on the host only.
gh auth status Your own gh login is missing. The driver reads PRs, checks and reviews and merges with it.
git fetch origin repo.path is wrong or you cannot fetch.
criteria catalog Fails when the criteria catalog that gates.verify.criteriaFrom names is missing from origin/<base> or invalid, with every error. Otherwise prints how many entries it has. Prints nothing without criteriaFrom.
origin Its owner and name must equal repo.github, case aside, so my-org/my-lib-next never passes for my-org/my-lib. The host must be github.com. An SSH host alias passes when ssh -G resolves it to github.com. HTTPS hosts are never resolved.
repository settings Fails when squash merges are disabled under merge.method: squash, when merge.admin is not false (the default auto counts) and you are not an admin, when a public repo is marked public: false, or when the repository cannot be read. Warns when the squash default is not the PR title with a blank message, and when a private repo is marked public: true.
agent identity Fails when the token's login is a maintainer or its permission is not exactly write, when the token is fine-grained (github_pat_…), which gets no Checks permission, when the token cannot read the repository (any answer but 200), when agents could fall back to a stored gh login, or when the token file is missing. The fallback check runs gh auth status without GH_TOKEN in the environment agents get. An info line says when gh would fall back to your keyring login with GH_HOST set, which agents never get. Warns when a classic token lacks the workflow or the read:org scope, and when there is no repo.agentToken at all. Without it, warns again when repo.maintainers is set, because comments agents post under your login count as your review feedback.
policy.merge Warns for auto: the driver merges without asking.
power macOS only. Warns on battery, because caffeinate cannot keep the Mac awake then. Never fails.
guard hook Feeding gh pr merge 1 --admin to the Bash guard does not end with exit code 2 and a rollout guard: reason, feeding it echo allowed does not end with exit code 0, or feeding it cat '<rollout>/ledger.json' does not end with exit code 2 and a rollout guard: reason. Only a guard that got the rollout directory on its hook command refuses the last one. The reason matters because the hook command ends with || exit 2, so a guard that never ran exits 2 too.
--live Under sandbox.runtime: docker it first proves the boundary: one container of the image over a scratch clone of the mirror, with the real mounts, the firewall and no agent, runs shell probes. A write to the skill directory and to /etc must fail. The rollout directory, repo.path and the mirror must be absent. A file created in the clone must belong to you. HTTPS to a host outside sandbox.allowedDomains must fail and HTTPS to api.anthropic.com must connect. The guard hook command must refuse gh pr merge and let echo through. An object rewritten in the clone must leave the mirror's copy unchanged. docker stop must end the container within 5 s. The first run creates the mirror when it is missing. Then, under either runtime, it starts a real headless claude -p (haiku, low effort) with the implementer's settings through the runtime: on the host in a scratch directory, under Docker in a container over a second scratch clone. The guard must refuse a gh pr merge, a push to main, a pnpm publish and a gh api -X PUT merge, and echo allowed must run. A command that never ran fails too, so a Claude login or quota problem shows up here. When the runtime checks fail, both are skipped.

Preflight does not check rulesets, CODEOWNERS or code scanning, that requiredChecks name real jobs, that you are in repo.maintainers, or that repo.install works. Accounts covers those.

sandbox build #

node $R sandbox build --dir D

Builds the image of the Docker runtime from sandbox/ in the skill directory, with docker build. It reads the versions of your claude (claudeBin) and gh and installs the same ones in the image. The tag is sandbox.image, else rollout-agent:<claude version>, the default image of the runtime. When the build succeeds it prints built <image>, and otherwise it exits with the code of docker build. A tool that prints no version stops it before the build. It works under either runtime, so you can build the image before you switch. Run it again after claude updates, because the default tag follows it and the driver never pulls an image. Any other subcommand prints the known ones and exits 1.

help #

node $R help

Prints the usage from the comment at the top of bin/rollout.mjs. So does node $R with no command. It needs no manifest.

Flags #

One parser serves every command, so every command accepts every flag and ignores the ones it does not use. An unknown flag or a missing value prints the error and the usage, and exits 1.

flag default used by meaning
--dir D $ROLLOUT_DIR, else the current directory all but ui and help The rollout directory, the one that holds manifest.yaml. A leading ~ expands.
--only A,B every PR run The PRs this run drives, comma separated. Every command checks the ids against the manifest.
--dry-run off run Everything real except the merge.
--live off preflight Also proves the guard in a real headless agent. Under sandbox.runtime: docker it proves the container's boundary first.
--root ROOT $ROLLOUT_ROOT, else ~/.rollouts ui The directory whose rollouts the UI lists: every subdirectory with a manifest.yaml.
--port N random ui A port from 0 to 65535. 0 picks a free one.
--no-open off ui Prints the URL without opening the browser.
--read-only off ui Disables every control. The server refuses every command.
--all off hold, release The whole rollout in place of PR ids. With ids too, the CLI refuses the command and posts nothing.

Environment #

variable set by meaning
ROLLOUT_DIR you The default for --dir.
ROLLOUT_ROOT you The default root for ui. An empty value counts as unset.
ROLLOUT_ROLE the driver, for agents, repo.install and the ready and pre-verify commands The agent's role, install for repo.install or gate for the ready and pre-verify commands the driver runs. While it is set, the CLI refuses every command but status, card and help. It is the only ROLLOUT_* variable they get: the driver removes any other one it inherited. The Bash guard reads none of them. Its context, the rollout directory, the skill directory, the rollout's name, repo.github and the PR branch, is on its hook command.
GH_TOKEN, GH_CONFIG_DIR the driver, for agents The bot's token and an empty gh config directory, when repo.agentToken is set. Under the Docker runtime a container gets the bot's GH_TOKEN and no GH_CONFIG_DIR.
GH_REPO the driver, for agents github.com/<repo.github>, with or without repo.agentToken, so agents' gh calls go to the manifest's repository. Agents never get GH_HOST, because with it gh reads your keyring login.
PATH the driver repo.pathPrepend goes first for the driver's own commands and for every agent. CLAUDECODE and CLAUDE_CODE_ENTRYPOINT are removed, so a driver started inside a Claude Code session does not make its agents look nested. Under the Docker runtime agents, the install and the commands do not get it: the driver uses it to find the docker client, and a container has the image's own PATH.
DOCKER_HOST you The daemon the Docker runtime and sandbox build use. The driver runs the docker client with your HOME and every DOCKER_* variable, so without it the current Docker context picks the daemon, as in your shell.

How commands reach the driver #

approve, note, retry, hold and release never write the ledger. Each writes one small JSON file into inbox/, first under a dot-prefixed name and then renamed, so the driver never reads half a command. A hold or release of several PRs is one file. The CLI prints a short confirmation and returns.

  • A running driver watches the inbox and applies a command within about a second. A burst of commands becomes one tick.
  • Without a driver, the files wait and apply when the next run starts.
  • Each command applies on its own, and so does each PR of a hold or release. One that is not a JSON object, names no PR or a PR the manifest no longer has, is an approve without a valid at time, or fails while it applies shows up as command-rejected in events.jsonl, with the reason. A refused approval shows up as approval-rejected. The rest of the batch still applies.
  • Entries that are not files are skipped. A file the driver cannot delete is rejected instead of applied, on every tick until someone deletes it.

stop and the UI's Start are different: stop signals the driver's process and Start launches one. The UI writes the same inbox files as the CLI for everything else.
