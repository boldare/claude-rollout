Security

hooks/guard-bash.mjs · lib/settings.mjs · lib/server.mjs

What protects what in a rollout, and what does not. Hard boundaries hold even against an agent that tries to break them. Seatbelts stop accidents and naive prompt injection, not a determined attacker.

Who and what #

  • Agents run headless as the maintainer's OS user, with the settings from lib/settings.mjs.
  • They read untrusted input: repo content, CI logs and PR comments. The driver passes on only comments by repo.maintainers (feedbackFor in lib/github.mjs), but an agent can read the others with gh.
  • The assets are the base branch, published packages, credentials, the rollout's control plane (manifest, inbox, ledger) and the local briefs, which may name clients.

Hard boundaries #

These are enforced where the agent cannot edit them.

  • The bot account's GitHub role and the rulesets. The bot has the Write role and no bypass. A merge needs a maintainer's review and green checks. See Accounts and the preflight check of repo.agentToken.
  • npm trusted publishing with tokens disallowed. Set on npmjs.com, see Accounts.
  • The UI's network checks. The UI listens on 127.0.0.1 and checks Host and Origin (handle in lib/server.mjs), so other web pages cannot reach it through DNS rebinding or CSRF. See The web UI.

The limit, stated plainly. These hold against the bot's token. Agents run as you, so any credential your user can read (your gh login, ~/.npmrc, SSH keys) is within their reach. A boundary against a hostile agent needs another OS user, a VM or a container. This repo provides none.

The driver's gate #

The driver never trusts an agent's report. It merges only what lib/judge.mjs passes, on facts it reads from GitHub and git (collectFacts in lib/github.mjs): the PR, its diff and commits, its reviews and the check runs on the exact head. That is hard against a wrong or false report. The full list of checks is on How it works.

It is not a boundary against an agent that attacks the driver's own files (code, ledger, inbox). Only the seatbelts below protect those.

Guard rails for agents #

Every agent gets the same layers, in two strengths.

  • Worker: the implementer and the fixer. They edit files, commit, push their own branch and open the PR.
  • Read-only: the verifier and both brief agents (readOnlyRole in lib/settings.mjs). They read, build and test, and change nothing.

Permission rules

Each agent starts with --settings from agentSettings. Deny rules win over allow rules in any permission mode. Agents run with --permission-mode auto and --permission-prompts none, so anything that would ask for permission is denied instead of hanging a headless run.

worker read-only
denied Bash gh pr merge, gh pr review, gh pr close, gh repo, gh release, gh secret, gh variable, gh workflow, gh ruleset, npm publish, pnpm publish, pnpm release, pnpm run release, pnpm changeset publish, git push origin main*, git push origin HEAD:main*, and the same two for repo.base
denied files Edit and Write under the rollout directory and the skill directory. The same, plus Edit, Write and NotebookEdit everywhere. They are also passed as --disallowedTools.
allowed Bash git *, pnpm *, node *, gh pr create|edit|view|checks|list, gh run view|list|rerun, gh api * git diff|log|show|status|rev-parse, pnpm *, node *, gh pr view|checks|diff, gh run view, gh api *
attribution Off for commits and PRs.
hook guard-bash.mjs worker on every Bash call guard-bash.mjs verifier on every Bash call

The push deny rules name main and repo.base. For every other branch, the guard and the pre-push hook hold the line, since both allow pushes to the PR branch only.

The Bash guard

hooks/guard-bash.mjs reads each Bash call before it runs. It exits with code 2 to refuse, and the agent gets rollout guard: … with the reason. It sees the Bash tool only, the file tools are covered by the permission rules. It fails closed. An empty payload, one that is not JSON or has no command string, and an error inside the guard also exit 2, because a PreToolUse hook blocks only with that code. It also runs when the skill directory is reached through a symlink, even under Node's --preserve-symlinks-main, on the command line or in NODE_OPTIONS.

It splits a command line on ;, &&, ||, |, &, newlines, $(, backticks, parentheses and braces. It deletes quotes and backslashes, so sh -c "git push origin main" and p"u"sh read as what they are. Quoting is not honoured on purpose: a forbidden word inside a string still blocks.

Refused for every agent

  • The control plane. Any command that names the rollout directory, the installed skill (ROLLOUT_HOME and any .claude/skills/rollout), the rollout's name as a path, or the push markers rollout-branch, rollout-pushurl and rollout-ready.
  • The environment the guard relies on. Setting GH_TOKEN, GH_CONFIG_DIR, GITHUB_TOKEN, GH_HOST, GIT_SSH*, GIT_CONFIG_*, GIT_DIR, GIT_WORK_TREE or any ROLLOUT_* variable, unsetting a ROLLOUT_* variable, and the --git-dir, --work-tree and --config-env switches.
  • Git settings that switch off hooks or reroute pushes. hooksPath, credentials, push URLs, sshCommand, url.*, remote.* and alias.*, whether through git config or a -c key=value override, and git config --remove-section or --rename-section.
  • Git commands that rewrite or bypass. git remote add|set-url|rename|remove|rm|set-head, git update-ref, send-pack, http-push, receive-pack, filter-branch, replace, git commit --no-verify or -n, git tag, and git branch -d|-D|-m|-M.
  • GitHub administration. gh repo, release, secret, variable, workflow, ruleset, alias, extension, codespace, gpg-key, ssh-key, cache and attestation. gh auth except gh auth status without the token. gh pr merge|review|close|reopen|lock|unlock.
  • Writes through the API. gh api graphql, and gh api with any method but GET, or with fields and no method. Raw curl, wget, http, https or xh calls to api.github.com, uploads.github.com, registry.npmjs.org or registry.yarnpkg.com.
  • Releases. npm, pnpm, yarn, npx, pnpx, bun or bunx with publish, release, version-packages, unpublish, dist-tag, deprecate, owner, adduser, login, logout or token. <tool> version. changeset version, publish, tag and pre, run directly, through a package manager, as @changesets/cli or through a path such as node_modules/.bin/changeset. changeset add and changeset status stay allowed.

Pushes from a worker

A worker pushes only with git push origin <refspec>, where every refspec targets $ROLLOUT_BRANCH. The guard refuses:

  • a push without an explicit refspec, because a bare git push is too easy to aim at the wrong branch
  • any remote but origin
  • --force, -f, --mirror, --all, --tags, --delete, -d, --prune, --no-verify and --repo
  • a + refspec and any refspec that deletes a remote ref
  • a push at all when ROLLOUT_BRANCH is not set

--force-with-lease on the agent's own branch stays allowed, so an agent can rewrite its own commits.

On top for the read-only role

  • git commit, push, rebase, merge, reset, clean, stash, cherry-pick, revert, tag, am, apply, checkout, switch, restore, update-ref, branch and worktree. The verifier stays on the PR head it was given.
  • gh pr create|edit|comment|ready and gh issue.

A seatbelt, not a sandbox. A regex guard can be fooled by a command it does not model. The guarantees that matter are also enforced elsewhere: the pre-push hook, no npm credentials in the agent environment, and the gate re-checking every claim on GitHub. rollout preflight --live proves in a real headless agent that the guard refuses a merge, a push to main, a publish and a gh api write.

Git hooks

Every worktree gets its own core.hooksPath, pointing at git-hooks/ in the skill directory. The hooks cover git push however it starts: an alias, a script or a tool.

  • pre-push reads the allowed branch from rollout-branch, a file the driver writes into the worktree's git directory, never from the environment. It refuses any other ref and any deletion. When the driver set up a push URL, it refuses any other URL too, so nothing reaches GitHub through your SSH remote.
  • commit-msg allows exactly one subject line of at most 72 characters. No body, no trailers.

With repo.agentToken set, each worktree pushes over HTTPS to repo.pushUrl through gh auth git-credential, so pushes use the bot's token and never your SSH key.

The environment

Each agent starts from the driver's environment, with repo.pathPrepend first on PATH and these changes (makeEnv, agentGitHubEnv, runAgent).

variable value why
GH_TOKEN the contents of repo.agentToken Agents act on GitHub as the bot.
GITHUB_TOKEN empty No second token to fall back on.
GH_CONFIG_DIR <rollout>/.gh-agents, empty gh cannot fall back to your stored login when the token is dropped.
GIT_TERMINAL_PROMPT 0 Git fails instead of asking for a password.
ROLLOUT_BRANCH the PR branch, empty for read-only roles The one branch the guard lets a worker push.
ROLLOUT_ROLE, _ID, _DIR, _HOME, _NAME role, PR id, rollout directory, skill directory, rollout name The guard's context, and the CLI's refusal to take orders from an agent.
NPM_CONFIG_USERCONFIG <rollout>/.npmrc-agents, with no credentials Every publish path fails for lack of auth.
NPM_TOKEN, NODE_AUTH_TOKEN empty The same.
CLAUDECODE, CLAUDE_CODE_ENTRYPOINT removed A driver started from a Claude Code session must not make its agents look nested.

Everything else passes through, HOME and your Claude login included. That is why the limit under Hard boundaries holds. Without repo.agentToken the GitHub variables are not set at all, agents act on GitHub as you, and preflight warns about it.

The CLI refuses agents

With ROLLOUT_ROLE set, bin/rollout.mjs runs only help, status and card. An agent cannot run the driver, approve, note, retry, hold, pause, stop or open the UI, even if it finds the skill.

The web UI #

rollout ui runs as your user on a local port. Agents run as your user too and can reach any local port, so the server trusts no caller by default (lib/server.mjs).

  • Loopback only. It listens on 127.0.0.1, never on a network interface.
  • Host check. Every request must carry Host: 127.0.0.1:<port> or localhost:<port>, otherwise it gets 403 bad host. A page on another domain that resolves to 127.0.0.1 still sends its own name, so DNS rebinding fails.
  • Origin check. Every request that is not a GET must carry the UI's own origin, otherwise it gets 403 bad origin. The server sends no CORS headers, so another origin cannot read an answer either.
  • The token. 32 random bytes, made at start, kept only in memory and compared in constant time. Every /api call needs it as a Bearer header, or it gets 401. It travels in the URL fragment, which browsers never send, so it stays out of request lines and logs. It is still printed in the terminal and kept in the browser history.
  • Headers. A Content Security Policy of default-src 'self'; frame-ancestors 'none'; base-uri 'none': no inline scripts or styles, nothing from other hosts, no framing. Plus Cache-Control: no-store, X-Content-Type-Options: nosniff and Referrer-Policy: no-referrer.
  • Narrow input. Static files come only from ui/, only as .html, .js, .css or .svg, with no dotfiles and no ... A rollout name from a URL must stay one directory below the root. Commands must be application/json, at most 64 KiB, and pass parseCommand in lib/control.mjs.
  • No approvals. approve is not a UI command, so nothing that reaches the page can approve a merge. --read-only makes the server refuse every command with 403.
  • Text, never HTML. Titles, verdicts, logs and transcripts are untrusted agent output. The page builds every element from text, and test/ui.test.mjs fails on innerHTML and its relatives in ui/.

The token stops a plain curl from another local process. It does not stop code that can read your terminal, your browser history or your files, which is everything an agent running as you can do. Use rollout ui --read-only when you only watch.

What to do #

  • Set up the repository as Accounts describes.
  • Run rollout preflight --live before the first run. It proves the guard in a real headless agent.
  • Review the workflow files that rollout card flags before you approve a PR.
