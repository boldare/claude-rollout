Accounts

lib/identity.mjs · lib/github.mjs · lib/judge.mjs

A rollout acts on GitHub with two identities: yours and a bot's. The agents talk to Claude with your login. This page sets up all three and explains what each one may do.

Two GitHub identities #

The driver uses your own gh login. Agents never get it: they act as a separate bot account whose token repo.agentToken points to.

What Who Where
Read PRs, reviews, comments and check runs you collectFacts, feedbackFor
Create the rollout:<name> label you ensureLabel
Set the rollout-stage: and rollout-reason: labels you setStageLabels
Merge, and delete the merged branch you merge, deleteRemoteBranch
Fetch your remote fetchOrigin
Push the PR branch, open and edit the PR bot runAgent, agentEnv
The driver's own rebase push bot rebaseWorktree
Replies in review threads and the summary comment bot replyAsAgents, commentAsAgents

Without repo.agentToken every row is you. Agents push through your normal remote, which may use your SSH key, and the driver's replies go out under your name. Preflight warns: "agents act on GitHub as you".

The driver's replies and summary comment end with a hidden <!-- rollout-driver --> line, so the driver never reads them back as your feedback. A comment an agent posts under your login has no marker, and it counts as your review feedback. Preflight warns about this when repo.maintainers is set.

The bot account #

Agents open PRs and push as a separate GitHub account, never as you.

  1. Create the account and invite it with the Write role

    Preflight requires its permission on the repository to be exactly write, and its login to be outside repo.maintainers. Admin fails the check, unless the account is an admin with a limited token.

  2. Create a classic token with the repo and workflow scopes

    workflow matters only for PRs that change .github/workflows/, and preflight warns when it is missing. Preflight reads the scopes from the x-oauth-scopes header. A fine-grained token has no scopes, so preflight warns that it cannot see the token's Workflows permission.

  3. Save the token outside any repo 
    mkdir -p ~/.config/rollout
# paste the token, then Ctrl-D
cat > ~/.config/rollout/agent-gh-token
chmod 600 ~/.config/rollout/agent-gh-token

    Point repo.agentToken at the file. ~ is expanded.

An admin account with a limited token

Sometimes the agents' account has to be an admin, for example a shared machine account that owns the organization. An organization owner is an admin of every repository, and that role cannot be lowered for one repository. Set repo.agentAdmin: true and give the account a fine-grained token. Preflight then accepts the admin role only when the token cannot act as one (adminAgentCheck in lib/preflight.mjs):

  • The token is fine-grained: it starts with github_pat_. A classic token can do all the admin role can.
  • The token gets 403 or 404 from an endpoint of each admin permission: Administration, Secrets and Webhooks on the repository, and Administration on the organization, which manages its rulesets.
  • The account cannot bypass any ruleset on repo.base, the organization's included. GitHub's current_user_can_bypass, read with the token, must be never for each one. A role on the bypass list counts, so the admin role must not be there.
  • Branch protection on repo.base, if there is any, has "Do not allow bypassing the above settings" turned on. Preflight reads it with your login, which needs the admin role for that.

Any other answer, an error or no answer fails. Create the token with the organization as its resource owner, only the repositories the rollouts work on, and these repository permissions:

Contents
read and write, to push the PR branch
Pull requests
read and write, to open and edit the PR and reply in review threads
Issues
read and write, for comments in the PR conversation
Checks, Commit statuses, Actions
read, to follow CI and read its logs
Workflows
read and write, only for PRs with allowWorkflows

Metadata is always on. Leave everything else at No access, Administration, Secrets and Webhooks above all.

Preflight checks once. The driver does not repeat these checks on every tick. Whoever later puts the admin role or the account on a bypass list, or gives the token an admin permission, opens a way around the rules. Run preflight again after such a change. It only looks at repo.github, so check every other repository the token reaches in its own rollout.

What the agents get

agentEnv in lib/identity.mjs sets this for every agent run:

GH_TOKEN
the contents of the token file
GITHUB_TOKEN
empty
GH_CONFIG_DIR
an empty .gh-agents/ in the rollout directory, so gh finds no stored login in it
GH_REPO
github.com/<github>, so every gh call goes to the manifest's repository, whatever the clone's remotes or gh repo set-default say
GIT_TERMINAL_PROMPT
0, so git never waits for a password

It removes GH_HOST, GH_ENTERPRISE_TOKEN and GITHUB_ENTERPRISE_TOKEN. With GH_HOST set, gh reads your keyring login even from the empty config directory. The guard refuses agent commands that set GH_HOST or drop the token (The Bash guard). Without repo.agentToken, agents get none of the variables above except GH_REPO, and GH_HOST is still removed.

Worktrees push over HTTPS to repo.pushUrl, by default https://github.com/<github>.git, with gh auth git-credential as the only credential helper (lib/worktree.mjs). The pre-push hook refuses any other URL and any branch but the PR's own, so your SSH key is never used for a push. Fetches keep using your normal remote.

policy.approval: github needs both repo.agentToken and repo.maintainers. The manifest is rejected otherwise (validateManifest in lib/manifest.mjs).

Repository rules #

A ruleset on the base branch

Add a branch ruleset on repo.base:

  • Require a pull request. Require one approval when policy.approval is github.
  • Require the status checks that repo.requiredChecks matches.
  • Block force pushes, and restrict deletions.
  • Requiring code scanning results is optional, see below.

The bypass list holds only the repository admin role, never the bot. With an admin bot the admin role must not be on it either: name the people who may bypass instead.

Squash merges and the admin role

  • Enable squash merges in the repository settings. Preflight fails without them. It also suggests the PR title with a blank message as the squash default and warns otherwise, although the driver passes its own subject and an empty body anyway.
  • Your own gh login must be a repository admin when merge.admin is set, and the default auto counts. Preflight checks it. The driver merges a PR you authored with --admin (needsAdmin in lib/judge.mjs), because GitHub does not let you approve your own PR.

CODEOWNERS

Add .github/CODEOWNERS that names the maintainers for .github/, the release configuration and CODEOWNERS itself, and make the ruleset require a code owner review. The bot is never a code owner.

This backs up repo.forbid and allowWorkflows. The driver's gate enforces both, GitHub does not.

Code scanning

Enable CodeQL default setup. When the ruleset requires its results, GitHub reports the merge state BLOCKED until they exist. The gate then waits with a reason, unless it merges with --admin.

The driver also reads the open alerts itself, for refs/pull/<n>/head and for the base branch. That is where default setup puts them. An alert open on the head and not on the base is new, and repo.codeScanning says what it does. An analysis of refs/pull/<n>/merge, which some advanced setups run, is not read.

npm trusted publishing #

Publish only from a GitHub Actions release workflow through OIDC, with no npm token anywhere.

On the driver side

  • repo.neverMerge keeps the release PR away from the driver.
  • The release workflow belongs in repo.forbid, as in examples/manifest.yaml.
  • Agents get no npm credentials: an empty npmrc, and empty NPM_TOKEN and NODE_AUTH_TOKEN (runAgent in lib/spawn.mjs).
  • Publish and release commands are denied in the agents' settings (lib/settings.mjs).

Pitfalls

  • Trusted publishing needs npm CLI 11.5.1 or newer. Upgrade npm in the workflow unless the Node version already bundles it.
  • The publishing job needs permissions: id-token: write.
  • The trusted publisher is set per package on npmjs.com: owner, repository, workflow file name (for example release.yml, the name only) and an optional environment. All must match exactly. Every package of a monorepo needs its own entry.
  • repository.url in each package.json must match the GitHub repository, or the publish fails.
  • Only GitHub-hosted runners are supported.
  • After the first trusted publish works, set the package to require two-factor authentication and disallow tokens, and delete any NPM_TOKEN secret.

Merge and approval #

policy.merge decides who merges. policy.approval decides how your approval reaches the driver. It matters only under merge: human, the one mode in which an approval counts.

policy.merge approval: inbox (default) approval: github
human (default) You read the card and run rollout approve <id>. The driver merges after the delay. A bot PR is approved by a maintainer's review on GitHub. A PR you authored still takes rollout approve. The driver merges after the delay.
manual The driver verifies, gates and rebases, then notifies you that the PR is ready to merge. You merge on GitHub, and the driver carries on from the merge. No approval counts, and rollout approve is refused.
auto The driver merges as soon as the gate passes. No approval counts, and rollout approve is refused. Preflight warns.

What counts as a GitHub approval

  • Only reviews by repo.maintainers count, and only the latest approval, change request or dismissal of each maintainer. A review that only comments does not count.
  • Any maintainer whose latest review asks for changes holds the merge.
  • An APPROVED review counts when it was submitted after the current patch appeared. Time decides, not the review's commit, because GitHub moves a review that is not dismissed to new heads (githubApproval in lib/judge.mjs).

What rollout approve binds to

rollout approve names the exact head and patch id the verifier passed. The driver rejects it when the PR is not verified any more, when its head changed, when it was posted before the verification finished, or when an agent is working on the PR.

Under merge: manual and merge: auto no approval counts. Under approval: github a bot PR is approved on GitHub. In these cases the CLI refuses rollout approve before it posts anything and says what to do instead. The driver refuses the same command if it reaches the inbox another way.

A new head with the same patch id, such as the driver's own rebase, keeps both the verification and the approval.

Bot PRs and approval: inbox. When the ruleset requires a review and the bot opened the PR, rollout approve satisfies the driver but not GitHub. The gate then waits with "GitHub still blocks the merge". Use approval: github, or merge.admin: true.

merge.admin

auto
the default: --admin only for a PR a maintainer authored
true
--admin on every merge
false
never. A PR you authored then cannot pass a ruleset that requires an approval

Without --admin, the gate waits until GitHub's merge state is CLEAN, HAS_HOOKS or UNSTABLE, so a missing ruleset requirement shows up as a reason instead of a refused merge.

The merge delay

Under merge: human the driver waits policy.mergeDelaySeconds (120 s) before it merges, counted from when the driver first sees the approval. That leaves room to notice an approval you did not expect and stop it with rollout pause.

  • For rollout approve, the window starts when the driver accepts the command.
  • For a GitHub review, it starts at the first gate pass that finds a maintainer's approval for the current patch, never at the review's own time. A review given while CI still runs gets the full window too.
  • Both send a notification when the window starts.
  • A change request or a dismissal clears a GitHub approval the driver has seen, so the next approval starts a new window.
  • The driver does not look for GitHub approvals while a PR is held or the rollout is paused. An approval it first sees after the release or the resume starts its window then.

The Claude side #

The login the agents use

There is no Anthropic account in the manifest. The driver starts every agent with its own environment (makeEnv in lib/sh.mjs), which drops only CLAUDECODE and CLAUDE_CODE_ENTRYPOINT. HOME stays the same. So each agent's claude authenticates exactly as it would in your shell:

  • with your stored login, a subscription or a Console account, when you have run claude and logged in, or
  • with ANTHROPIC_API_KEY, when it is exported in the shell that starts the driver.

On top of that, runAgent in lib/spawn.mjs adds only the bot's GitHub variables, the pinned GH_REPO, the ROLLOUT_* variables and the empty npm credentials, and removes GH_HOST. A driver started from the UI inherits the environment of the rollout ui process, so start the UI from a shell where claude works.

Check the login with the live preflight. Plain preflight only runs claude --version. preflight --live starts a real headless agent, so a login or quota problem shows up there as five failed checks that "never ran".

Model and effort

model defaults to opus, and the same --model goes to every role: brief writer and reviewer, implementer, fixer and verifier. Only the live preflight uses haiku.

Effort is one of low, medium, high, xhigh and max. Every PR sets effort.implement and effort.verify, and effort.brief defaults to xhigh.

Effort Good for
max Subtle runtime or concurrency work. Give the verifier xhigh then.
xhigh Public API or cross-package changes.
high Mechanical work across many files.
medium Docs.

Effort rises when a PR struggles (raiseEffort in lib/manifest.mjs). A second implement run goes one level up. Fix runs start at effort.implement and go one level up with each fix attempt after the second. The verifier and the brief runs keep their effort. max is the ceiling.

Budget and cost

  • Every run gets --max-budget-usd from policy.budgetUsd for its effort, after raising: low 3, medium 8, high 20, xhigh 35 and max 60 USD by default.
  • There is no cap per PR or per rollout. policy.attempts bounds how many runs of each role a PR gets before it escalates, and the costs show in status, the card and the UI.
  • A PR's cost is the sum of the total_cost_usd each run reports. On a subscription it is what the run would cost on the API, not a charge.
  • A run killed before it reported a cost gets an estimate from the list prices in lib/prices.mjs. The UI shows estimates apart and never adds them to the total.

Rate limits and spend limits

  • Temporary trouble: a rate or usage limit, an overload, a 429 or 5xx, a dropped connection, claude's own rate_limit, overloaded and server_error errors, or a rejected rate_limit_event. It still counts when the stall watchdog or the timeout killed the run. The run gives its attempt back, up to 5 times per PR, and the PR waits before its next try: 2, 4, 8 and so on minutes, at most 30.
  • Account trouble: a message about a spend limit, a credit balance, billing or an exceeded budget, or claude's own billing_error, account_on_hold and authentication_failed errors. The budget here is the account's, not the run's cap. The whole rollout pauses and notifies you. rollout resume continues it.
  • The run's budget cap: a run that reaches its own --max-budget-usd fails with "hit its budget cap ($N)". It is neither kind. It uses up its attempt and the rollout goes on.

What preflight checks #

Account Checked
Your gh login gh auth status, git fetch origin, that origin is repo.github on github.com, that squash merges are enabled, that you are an admin when merge.admin is set, and that repo.public matches the repository's visibility. Origin's owner and name must equal repo.github, case aside. An SSH host alias passes when ssh -G resolves it to github.com. An HTTPS origin must be on github.com itself. See preflight.
The bot That the token file exists, that its login is not a maintainer and has exactly the write permission, or admin with repo.agentAdmin and a token that cannot act as one (An admin account), that agents' gh has no stored login to fall back to in the environment agents get, and a warning without the workflow scope or for a fine-grained token. An info line says when gh would fall back to your keyring login with GH_HOST set. It is never a problem, because agents never get GH_HOST. Without repo.agentToken, one warning, plus a second one when repo.maintainers is set.
Claude claude --version. With --live, a real headless agent whose guard must refuse four forbidden commands and allow one harmless command.

Preflight does not check:

  • rulesets, CODEOWNERS, code scanning or npm trusted publishing
  • that requiredChecks names jobs your CI really has
  • that your own login is in repo.maintainers
  • that repo.install works
  • your Claude login, unless you pass --live

Run rollout preflight --live before the first run, and again after you change accounts or tokens. Security explains what these accounts protect and what they do not.
