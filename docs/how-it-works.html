How it works

lib/driver.mjs · lib/spawn.mjs · lib/judge.mjs

The driver is a plain Node process. It keeps the whole rollout in files, reads the truth from GitHub on every tick and starts one headless agent per step of a PR. This page follows that loop from the outside in.

A process, not a model #

rollout run is the orchestrator. No model decides what happens next, so a stalled chat session cannot stall a rollout. Everything the driver knows lives in the rollout directory, and every decision it takes is written down there.

  • One driver per rollout. It takes driver.lock with its pid. A second driver on the same directory refuses to start. A lock left behind by a dead process, or one without a real pid, is cleared.
  • A heartbeat. Every tick and every save writes heartbeat: a timestamp and a short note. status and the UI read its age to tell a live driver from a stuck one.
  • State on disk. ledger.json holds the state of every PR and is replaced atomically, through a temp file and a rename. events.jsonl only grows. logs/ keeps every agent transcript.
  • A live manifest. A changed manifest.yaml is loaded again on the next tick, without a restart. An invalid edit is rejected with a manifest-rejected event, and the previous manifest stays. A missing manifest.yaml is rejected the same way, once, and loads again when it is back.
  • Stop and resume. The first Ctrl-C, SIGTERM or SIGHUP stops the agents (SIGTERM, then SIGKILL after 5 s), saves and exits. A second signal exits at once. On the next run, every run that was in progress gets its attempt back and its PR becomes interrupted, or pending for a brief. An implementer or fixer then continues its own session, a verifier starts over and an unfinished brief is written again.

System map #

The overview has a short version of this map. This one adds the UI server and the worktrees, and the table below it shows which identity makes which GitHub call.

Who calls GitHub as whom

Caller Identity Calls
Driver your gh login Reads PRs, reviews, comments and check runs. Creates the rollout label, merges, and deletes merged branches.
Driver the bot's token The --force-with-lease push after a rebase, replies in review threads, and the summary comment after a fix.
Implementer, fixer the bot's token Pushes to the PR branch over HTTPS, gh pr create and edit, gh pr checks, gh run view, read-only gh api.
Verifier, brief agents the bot's token Reads only: gh pr view, checks and diff, gh run view, read-only gh api.

The bot's token is the file repo.agentToken names. Without it, every call runs as you, and preflight warns about that. Accounts explains the setup.

One tick #

Once started, the driver repeats one tick until every PR of the run is merged. A tick does this, in order:

  1. Beat. Write the heartbeat.
  2. Reload the manifest if the file changed.
  3. Apply the inbox. Every command file is read and deleted, then applied: approve, note, retry, hold, release, pause, resume and unhalt. Each command applies on its own, and a rejected one never stops the rest. A command that cannot apply is logged as command-rejected, a refused approval as approval-rejected.
  4. Fetch. git fetch --prune origin in the repository. A failed fetch logs fetch-failed, and the gate step is skipped for that tick, because a stale base would mislead it.
  5. Check outside dependencies. With --only, a dependency that is not in the run counts as merged once GitHub shows its branch merged into the base with the rollout label. One already merged is not looked up again. A failed lookup does not stop the others, and the driver logs outside-deps-failed with each dependency it could not check.
  6. Watch the base. After a rollout PR merges, by the driver or on GitHub, read the check runs on its merge commit. Red halts the rollout, green clears the watch. A failed read logs watch-base-failed and is tried again on the next tick.
  7. Sync every PR with GitHub. A merge or a close made on GitHub wins. A head that moved after verification is checked again. Then look for new maintainer feedback on the PR.
  8. Run the gate. Verified PRs go through the gate in priority order, then manifest order. PRs with an agent running or feedback waiting are skipped. The first merge or rebase ends this step, so there is at most one per tick. The step is skipped while the rollout is paused, halted or stopping, and in a tick whose fetch failed.
  9. Advance every PR in priority order, unless the rollout is paused. Briefs, implementers, fixers, verifiers and delegates start while slots are free, and READY claims are checked.
  10. Save the ledger.

Then the driver sleeps for policy.tickSeconds (60 s). A new file in inbox/ ends the sleep early, after a 500 ms pause that folds a burst of commands into one tick. Once every PR of the run is merged and no agent runs, the driver reports the release PR and exits.

  • A slot is one running agent. policy.concurrency caps them (2 by default). A brief holds one slot for its writer and reviewer together. Verifiers take slots too. Gate checks, rebases and merges do not.
  • The gate runs before slots are handed out. A conflict it finds on a high-priority PR then competes for a slot in the same tick, ahead of new briefs for lower-priority PRs.
  • The fetch, the dependency check and the base watch belong to no PR. A failure logs its event, and the rest of the tick runs. None of them count against a PR, and five failures in a row of one step notify you.
  • Errors belong to one PR. Every per-PR step runs inside guarded(). An error becomes an error event for that PR and the tick goes on. A PR counts one error per tick, and the count resets after a tick without one. Five erroring ticks in a row, with no agent running, escalate that PR alone, once. Any other error is a tick-error event, and the next tick starts as usual. Five failed ticks in a row notify you once.

The PR lifecycle #

Every PR in the manifest has one state in the ledger. The colours are the state badges of the UI board.

State What happens What moves it on
pending Waits for its dependencies to merge and for a free slot. Both there: briefing when the PR's brief file is missing, else implementing.
briefing A read-only writer drafts the brief from briefing.sources on a worktree of the base. A read-only reviewer checks it against the code and returns the final text. The driver writes the brief file and a .review-notes.md file next to it, and the PR goes back to pending. Open questions: blocked. A failed run: pending, after a backoff.
implementing The implementer codes in the PR's worktree, pushes, opens the PR and waits for CI. A READY report that names an open PR from the branch into the base: ready_claimed. A READY report that does not match GitHub: needs_fix. A READY report GitHub could not read: interrupted, checked again on a later tick (report-unchecked). BLOCKED: blocked. No report: interrupted.
ready_claimed The driver checks the claim itself. It re-reads the PR head, waits for CI on that exact SHA, then applies the rollout policy to the diff. Then it reads the new code scanning alerts on the head. CI green, no policy violation, no new alert and a free slot: verifying. CI red, CI still unsettled after ciStallMinutes, a violation or a new alert: needs_fix. A new alert under codeScanning.action: block: blocked. An alert from an analysis of an older commit: it stays here and waits for the analysis of the head.
verifying A fresh read-only verifier tries to refute READY for that SHA, against the brief's acceptance checklist. PASS from an untouched worktree for the claimed SHA: verified. FAIL: needs_fix. A PASS from a verifier that changed the tree, or for a stale SHA, is discarded: ready_claimed.
verified The verification is bound to the head SHA and the patch id. The gate runs on every tick. Gate merge: merged. Rebase: the driver rebases the branch itself. Fix, a conflict or a maintainer review: needs_fix. Block: blocked. A new head with a different patch: ready_claimed.
needs_fix Waits for a slot, with a reason and a note that explains it. A free slot: fixing.
fixing The implementer's own session, resumed with the reason. Without a session, a fresh one gets the whole protocol again. The same as implementing.
blocked Waits for you: a question from the agent, open questions about the brief, a gate block (for example the release PR or a draft), a code scanning block, or a PR closed on GitHub. rollout note answers it. An answer to brief questions gives the brief attempt back. rollout retry starts over with fresh attempts. With policy.delegate on, the delegate may answer first. After a code scanning block, dismiss a false positive on GitHub. Then rollout retry checks the claim again with no fix run.
escalated The attempts of a role ran out, or the PR had an error in five ticks in a row. rollout retry resets the attempts. rollout note sends an answer to a fix run. On a PR with no brief and no GitHub PR, the note goes to the brief writer instead.
interrupted A run ended without a report: a crash, a stop, a stall, a timeout or an outage. A READY report also waits here when GitHub could not be read to check it. A later tick resumes it. A parked READY report is checked again, with no agent run. An interrupted verifier re-checks the claim, an implementer with no session starts again, and anything else continues as a fix run. A PR with no brief file and no GitHub PR goes back to pending instead, so the brief writer runs first.
merged Merged by the driver, or on GitHub by you. The worktree, the local branch and the remote branch are removed. When an agent still runs, that waits until its run ends, and its report is ignored. Final.

Three flags sit next to the states:

  • Held is set on one PR by hold. It gets no new runs, rebases, ready notices or merges until release. A running agent finishes its step. Sync and feedback still run.
  • Paused applies to the whole rollout. No new runs start and nothing merges. Running agents finish.
  • Halted applies to the whole rollout after the base went red behind a merge. Only merges stop. Agents keep working until unhalt.

Roles #

Every agent is the same claude -p binary with a different prompt, session, set of permissions and report schema. The prompts live in prompts/ and the schemas in schemas/, in the skill's directory.

Role Prompt Session May Reports
brief writer brief-write.md, the briefing sources for the PR, every earlier question with your answer new Read the base branch. Edit, Write and NotebookEdit are denied. brief.json
brief reviewer brief-review.md, the sources, the writer's brief without its questions and notes new The same as the writer. brief.json
implementer implement.md: the protocol, the brief, the verify recipe, the scope, the forbidden paths new, kept as the PR's session Edit, commit, push its own branch, open and edit the PR, wait for CI. ready.json
fixer fix.md: the reason, the note, the current head the implementer's, with --resume The same as the implementer. ready.json
fixer, fresh resume-fresh.md, which wraps the whole implement prompt new, when the old one is gone The same as the implementer. ready.json
verifier verify.md: the SHA, the READY report, the recipe without steps that rewrite files new, every time Read, build and test. No edits, commits, pushes or GitHub writes. verdict.json
delegate delegate.md: the question and evidence, the sources, the brief and earlier answers new, every time The same as the verifier. delegate.json
  • Effort comes from the PR's effort and rises on retries. The implementer goes up one level per attempt after the first. Fix runs use the implement effort and go up from the third fix attempt. The verifier keeps effort.verify, and briefs use effort.brief (xhigh by default).
  • Budget. Every run gets --max-budget-usd from policy.budgetUsd for its effort. There is no cap for a whole PR or rollout.
  • Model. Every role runs the manifest's model, opus by default.

The delegate

The delegate is off unless policy.delegate is set. When a PR blocks on a question of an allowed kind, brief questions and needs-decision by default, the driver starts it in a free slot. The PR stays blocked while it runs.

It reads the question and the evidence, the plan and design notes, the brief, every earlier answer and the code. It answers only what the plan decides, and escalates the rest: a silent or ambiguous plan, security, credentials, publishing, releases, weakened tests, a wider scope. An answer reaches the agent the same way your note does, prefixed as the delegate's. An escalation leaves the PR blocked for you. Both notify you.

Each question gets one run, also when that run fails, and a PR at most maxPerPr runs. A note of yours always wins. It applies at once, also while the delegate runs, and the delegate's late answer is dropped.

One agent run #

The driver talks to a running agent in two ways. It writes the prompt to the agent's stdin, and it reads the agent's stdout and stderr. Everything else the agent does goes through the worktree and GitHub, where the driver checks it.

The command

The prompt goes in on stdin, because briefs and brief sources get large. The working directory is the PR's worktree.

claude -p --model <model> --effort <effort> \
  --output-format stream-json --verbose \
  --json-schema <schemas/ready|verdict|brief|delegate.json> \
  --permission-mode auto --permission-prompts none \
  --settings <deny and allow rules, the guard hook> \
  --max-budget-usd <policy.budgetUsd[effort]> \
  [--disallowedTools Edit Write NotebookEdit] # verifier, brief and delegate roles
  --session-id <new uuid> | --resume <the PR's session>
Environment
Yours, with repo.pathPrepend first on PATH, plus the ROLLOUT_* variables and no npm credentials. With a bot token also its GH_TOKEN, an empty GITHUB_TOKEN, a GH_CONFIG_DIR that points at an empty directory and GIT_TERMINAL_PROMPT=0.
Settings
Deny rules for merges, reviews, repo admin and publishing, allow rules per role, attribution off, and a PreToolUse hook that runs hooks/guard-bash.mjs on every Bash call. Security has the details.
Watchdogs
No output for policy.stallMinutes (20) ends the run, and so does the role's policy.timeouts. SIGTERM first, SIGKILL 10 s later.
Transcript
stdout goes unchanged into logs/<id>-<NN>-<role>.jsonl. The UI shows it on the PR page's runs tab.
Result
The last type: "result" line carries structured_output (the report), total_cost_usd, session_id and the permission denials. A run without that line, with is_error, or without a report has failed. The driver also reads claude's API error lines (is_api_error_message with an error kind) and rejected rate_limit_event lines. They tell an outage or an account problem apart from a real failure. The agent's own result text is shown as the error but never classifies it.

The reports

--json-schema makes the agent end with a JSON document in a fixed shape. The driver acts on a few fields and checks what it can on GitHub and in the worktree. The rest goes on the card for you.

Schema Used by Fields
ready.json implementer, fixer status (READY or BLOCKED) and summary are required. READY also needs pr and headSha, which the driver checks, not the schema. blocked with a kind, a question and evidence for BLOCKED. Optional: checks, localVerification, checklist, expected, filesChanged, changeset, deviations, and addressed for review comments.
verdict.json verifier verdict (PASS or FAIL), sha, summary, checklist with pass, fail or unverifiable and evidence per item, blocking, nonBlocking. All required.
brief.json brief writer, reviewer brief (markdown), expectedFiles, changesetBump, questions, notes. All required. The expected files become the PR's scope when the manifest has none.
delegate.json delegate decision (answer or escalate), answer (empty for escalate), planRefs and reasoning. All required. The answer goes to the agent, the rest to the card.

How a fix resumes

A fix run resumes the implementer's session with --resume, so the agent keeps everything it knew. Its prompt names the reason (for example CI is red, rollout policy, verifier findings, merge gate, rebase conflict or maintainer review), a note with the details and the current head. A note you queued is appended. If the session is gone, the driver drops it, and the next fix starts a new session with the whole implement prompt inside resume-fresh.md.

The merge gate #

judge() in lib/judge.mjs is a pure function of facts the driver read from GitHub and git. It never looks at what an agent said. For a verified PR it returns one action: merge, rebase, fix, wait or block. It checks, in this order:

  1. Wait while the rollout is halted or the PR is held.
  2. Block when there is no PR for the branch, the PR is closed, it is the release PR (repo.neverMerge), it is a draft, its base or head branch is wrong, or the rollout label is missing. A PR merged on GitHub while the gate reads it waits instead, and the next sync records the merge.
  3. Wait for dependencies, and for a verification of the current patch id.
  4. Wait for approval, with policy.merge: human only. With policy.approval: github and a PR that no maintainer authored, that is a maintainer's GitHub review submitted after the current patch appeared, with no changes requested. Otherwise it is rollout approve for this patch. In manual mode your own merge is the approval, and auto needs none.
  5. Fix on a policy violation: a forbidden path, .github/ without allowWorkflows, a package version edit, a removed or missing changeset, a bump above maxBump, a denylisted term, or a commit with more than one line.
  6. Rebase when the branch is behind the base or conflicts with it.
  7. Wait until GitHub reports the PR as mergeable.
  8. Fix when CI is red on the head. Wait while it is pending or a required check has not appeared.
  9. Fix or block on new code scanning alerts at or above repo.codeScanning.minSeverity, as its action says. Wait while an alert comes from an analysis of an older commit.
  10. Wait while the base branch is not green.
  11. Wait for GitHub's own merge state, unless the merge uses --admin or the mode is manual. It must be clean, or has hooks, or unstable. BLOCKED usually means a ruleset requirement such as a review or code scanning results.
  12. Merge. In manual mode the driver notifies you that the PR is ready to merge instead.

With merge: human the driver then waits policy.mergeDelaySeconds (120 s), counted from when it first sees the approval, so a pause can still stop it. A dry run logs would-merge and stops there. Otherwise it merges the exact head it judged: 

gh pr merge <n> --<method> --match-head-commit <sha> \
  --subject "<title> (#<n>)" --body "" [--admin] # method: squash by default
  • --admin is added when repo.merge.admin is true, or when it is auto and a maintainer authored the PR, because GitHub does not let authors approve their own PR.
  • GitHub refusing the merge is a state to wait in, not an error. The gate records it and you get a notification.
  • A merge GitHub has not confirmed, accepted but with no merge commit to read yet (a merge queue, for example), logs merge-unconfirmed. The PR stays verified until the next sync sees it merged. Then the driver records the merge, notifies you and cleans up. Nothing is removed before that.
  • Rebases are the driver's own work. It rebases the judged head onto the base in the worktree and pushes with --force-with-lease on that head, as the bot. A conflict aborts the rebase and goes back to the implementer with the conflicting files. When the patch id stays the same, the verification and the approval carry over to the new head.
  • The release PR ("chore: version packages" by default) is never merged, because merging it publishes. After the last PR, the driver finds it by title and tells you to merge it.

Failures and recovery #

The driver has to keep going for hours, unattended. This is how it treats what goes wrong.

What happened What the driver does
A run that did no work Stopped by the driver, a transient error (rate or usage limit, overload, HTTP 429 or 5xx, a dropped connection, claude's rate_limit, overloaded or server_error, a rejected rate_limit_event), an account error, or under $0.01 and under 60 s. The attempt is given back, at most five times per PR. rollout retry starts that count over.
Any failed run Backs off before the next one: 2, 4, 8, 16, then 30 minutes. The streak resets on a successful run. A stop by the driver does not count. rollout retry starts the streak over.
Attempts ran out policy.attempts caps each role (implement 2, fix 4, verify 3, brief 2). The next launch escalates the PR. A verified PR gets its verify attempts back.
Errors in five ticks in a row A PR counts one error per tick, and a tick without one starts the count over. After the fifth erroring tick in a row, guarded() escalates that PR as soon as no agent runs for it. An escalated PR is not escalated again. The other PRs go on.
A driver-wide step failed A failed fetch, outside-dependency check or base watch logs fetch-failed, outside-deps-failed or watch-base-failed and counts against no PR. The rest of the tick runs, except the gate after a failed fetch. Five failures in a row of one step notify you.
Five failed ticks Each failed tick is a tick-error event with the number of failed ticks in a row, and the next tick starts as usual. The fifth in a row notifies you.
A READY report GitHub could not read The PR becomes interrupted with a report-unchecked event, and the report waits. A later tick checks it again with no agent run and no attempt spent. A report that names a PR GitHub does not know still goes back to the implementer.
A merge GitHub has not confirmed Logged as merge-unconfirmed. The PR stays verified and nothing is cleaned up until the next sync sees it merged.
A run ended without a report The PR becomes interrupted and resumes on a later tick. So does every run in progress when the driver stops.
The session is gone The driver forgets it, and the next fix starts a new session with the full protocol.
No output, or too long The stall watchdog and the role's timeout kill the run. It ends as failed and the PR becomes interrupted. Stderr from before the kill still counts, so a rate limit there gives the attempt back.
A run hit its budget cap It reached --max-budget-usd and fails with "hit its budget cap ($N)". It counts as an attempt, and the rollout does not pause.
The base went red after a merge The rollout halts. Merges stop, agents go on, until you fix the base and run unhalt.
An account limit A spend limit, credit balance, billing or account budget error, or claude's billing_error, account_on_hold or authentication_failed, pauses the whole rollout until resume. A notification says so.
A broken manifest edit Rejected with a notification. The previous manifest stays in use. A missing manifest is rejected the same way, once.
GitHub refused the merge The gate waits and notifies. Nothing counts as a failure.
Code scanning could not be read A repo without code scanning answers 404 or 403. The driver logs code-scanning-unavailable once per PR and goes on without it. Any other error, a rate limit included, counts as an error of that PR.

Maintainer feedback on GitHub #

You can review a rollout PR on GitHub as you would any other. The driver turns your comments into a fix run.

  • Only people in repo.maintainers count. It reads their inline review comments, review bodies (commented or changes requested) and conversation comments. With no maintainers set, it reads none. Comments that end with the driver's <!-- rollout-driver --> line never count, even under a maintainer's login (maintainerFeedback in lib/github.mjs).
  • Bot comments, such as code scanning or Copilot reviews, never count. Code scanning alerts reach the gate as data from the API instead.
  • It looks at PRs that are ready_claimed, verified or needs_fix, while no agent runs for them.
  • It waits until you have been quiet for policy.feedbackQuietMinutes (3), so a review in progress is not cut short. Meanwhile the gate skips the PR.
  • Then it drops the verification and sends the PR to a fix run with every new comment, the file and line, and the code it refers to. The fixer lists each comment id in addressed, with what it did.
  • After the fixer reports READY, the driver answers each inline thread with that action and the new short SHA, as the bot. Without repo.agentToken the replies go out under your login. Everything else is summed up in one PR comment. Handled comments are remembered by id and never sent twice.

Notifications #

The driver sends desktop notifications through osascript on macOS and notify-send on Linux. Other platforms get none, and a notification that fails is ignored. Nearly every notice is also a line in events.jsonl. The gate's notices about a missing approval or GitHub still blocking show up there only as gate-wait.

  • Waiting for you: verified (with the next step), blocked, escalated, ready to merge in manual mode, brief questions, a question the delegate passes to you, the delegate's run limit for a PR.
  • Decisions: approval accepted or rejected, a GitHub approval the driver has seen, merged, would merge in a dry run, an answer from the delegate.
  • Trouble: halted, paused by an account limit, merge refused or blocked by GitHub, the head moved after verification, the verifier changed the tree, a dependency outside the run, a rejected manifest, five failed ticks in a row, five failures in a row of a driver-wide step.
  • The end: all PRs merged, with the release PR to merge.

Notices that could repeat on every tick are sent once per patch or head.
