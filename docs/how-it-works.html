How it works

lib/driver.mjs · lib/spawn.mjs · lib/judge.mjs

The driver is a plain Node process. It keeps the whole rollout in files, reads the truth from GitHub on every tick and starts one headless agent per step of a PR. This page follows that loop from the outside in.

A process, not a model #

rollout run is the orchestrator. No model decides what happens next, so a stalled chat session cannot stall a rollout. Everything the driver knows lives in the rollout directory, and every decision it takes is written down there.

  • One driver per rollout. It takes driver.lock with its pid. A second driver on the same directory refuses to start. A lock left behind by a dead process, or one without a real pid, is cleared.
  • A heartbeat. Every tick and every save writes heartbeat: a timestamp and the line of the last tick. status and the UI read its age to tell a live driver from a stuck one.
  • State on disk. ledger.json holds the stage and status of every PR and every agent run, and is replaced atomically, through a temp file and a rename. Its version says which shape it has. A driver migrates an older ledger once, when it starts. The driver, status and the UI refuse a ledger that a newer driver wrote. events.jsonl only grows. logs/ keeps every agent transcript.
  • A live manifest. A changed manifest.yaml is loaded again on the next tick, without a restart. An invalid edit is rejected with a manifest-rejected event, and the previous manifest stays. A missing manifest.yaml is rejected the same way, once, and loads again when it is back.
  • Stop and resume. The first Ctrl-C, SIGTERM or SIGHUP stops every agent run (a process gets SIGTERM, then SIGKILL after 5 s), waits up to 15 s for the runs to end, saves and exits. A second signal exits at once. On the host each agent runs in a process group of its own. A stop, the timeout and the stall watchdog signal that group, so they also end what the agent started, and a Ctrl-C in the terminal reaches the agents only through the driver. A stop and a hard end (a kill, a crash, a reboot) resume the same way, within the five refunds of a PR: every run that was in progress gets its attempt back and its PR waits on the stage of its run, with a no-report fix on implement. A fix run keeps its fix, with its reason and note, and a delegate run gives its run back and hands its question back. A run cut off by a hard end, or still going when the stop saves, is ended this way by the next run at its start. Before any role resumes, that start ends the agent process of every run with no end. On the host it signals the run's process group, and only while the pid still has the start time the run recorded. A pid with another start time is left alone. Under Docker it removes the run's container with docker rm --force. Each such run logs outlived-process with its outcome, and a process the start could not end notifies you. An implementer or fixer then continues its own session, a verifier starts over and an unfinished brief is written again. A stop kills running ready and pre-verify commands and their children the same way and drops their results. The next run cleans what they left in the worktree, then runs them again. Commands that passed are kept in the ledger for their head and their lists, so a restart does not run them again on that head.

System map #

The overview has a short version of this map. This one adds the UI server and the clones, and the table below it shows which identity makes which GitHub call. Agents run on your machine, or in containers under sandbox.runtime: docker.

Who calls GitHub as whom

Caller Identity Calls
Driver your token, from gh auth token Reads PRs, reviews, comments and check runs, creates the rollout label and deletes merged branches, through its REST client, lib/gh.mjs. Merges with gh pr merge, its one gh call.
Driver the bot's token The --force-with-lease push after a rebase. Under the Docker runtime, also the fetches in a PR's clone once the clone is set up. Through lib/gh.mjs, replies in review threads and the summary comment after a fix.

The bot's token is the file repo.agentToken names. Without it, every call runs as you, and preflight warns about that. Accounts explains the setup.

Every GET the driver repeats sends back the ETag of its last answer, while the driver still holds that answer. GitHub answers 304 when the body did not change, and a 304 costs no rate limit. The ETag does not cover the Link header, which names the next page of a list. So when the driver reads a list page by page and a full page answers 304, it reads the page after it too.

One tick #

Once started, the driver repeats one tick until every PR of the run is merged. A tick does this, in order:

  1. Beat. Renew the time of the heartbeat.
  2. Notice a sleep. A gap since the end of the last tick that is more than a minute longer than policy.tickSeconds is sleep. The driver logs machine-slept with its minutes and opens a two-minute window in which a failed GitHub request or gh or git call is an outage.
  3. Reload the manifest if the file changed.
  4. Apply the inbox. Every command file is read and deleted, then applied: approve, note, retry, hold and release. Each command applies on its own, and so does each PR of a hold or release. A rejected one never stops the rest. A command that cannot apply is logged as command-rejected, a refused approval as approval-rejected.
  5. Fetch. git fetch --prune origin in the repository. A failed fetch logs fetch-failed, and the gate step is skipped for that tick, because a stale base would mislead it. A fetch lost to an outage logs github-unavailable instead, and skips the gate too.
  6. Check outside dependencies. With --only, a dependency that is not in the run counts as merged once GitHub shows its branch merged into the base with the rollout label. One already merged is not looked up again. A failed lookup does not stop the others, and the driver logs outside-deps-failed with each dependency it could not check.
  7. Watch the base. After a rollout PR merges, by the driver or on GitHub, read the check runs on its merge commit. Red logs base-red and notifies once per merge. Green clears the watch. The watch stops nothing, because the gate waits on a red base by itself. A failed read logs watch-base-failed and is tried again on the next tick.
  8. Sync every PR with GitHub. A merge, a close or a reopen made on GitHub wins. A merge on GitHub stops the PR's agent in the same tick, if one runs. A head that moved after verification is checked again. Then look for new maintainer feedback on the PR.
  9. Run the gate. PRs on merge go through the gate in priority order, then manifest order, a gate block and code scanning alerts included, so the gate reads them again every tick. PRs with an agent running or feedback waiting are skipped, and so are a closed PR, a refused merge and a PR escalated for errors. The first merge or rebase ends this step, so there is at most one per tick. The step is skipped while the rollout is held or stopping, and in a tick whose fetch failed.
  10. Advance every PR in priority order, unless the rollout is held. Briefs, implementers, fixers, verifiers and delegates start while slots are free, and READY claims are checked.
  11. Save the ledger.
  12. Measure. Write the line of the tick to the heartbeat, such as tick 4210 requests=7 cached=7 remaining=4870. The first number is how long the tick took up to the save, in milliseconds. requests= counts the GitHub API requests made during the tick, a retry included. The merge goes through gh pr merge and is not counted. cached= counts the requests GitHub answered with a 304. remaining= is the rate limit left on the maintainer's token, from the last answer that named it, or - before any did. The agents' token has a limit of its own, so its answers never set it. After a failed tick, the heartbeat says tick-error and the error instead.

A tick reads each GitHub fact once and shares it with every step that needs it: a PR, its reviews, its code scanning alerts and the check runs of a commit. A run that ends during the tick drops the reads of its PR, so its READY claim is checked against the PR after the push. The next tick reads everything again. For example, a verified PR waiting for approval, with repo.maintainers set, no open code scanning alert and check runs on the base tip, costs 7 GETs a tick:

  • the PR, for the sync and the gate
  • its reviews, for the feedback and the approval
  • its inline review comments
  • its conversation comments
  • the check runs of its head
  • the check runs of the base tip
  • its code scanning alerts

Then the driver sleeps for policy.tickSeconds (60 s). A new file in inbox/ ends the sleep early, after a 500 ms pause that folds a burst of commands into one tick. Once every PR of the run is merged and no agent runs, the driver removes the mirror, reports the release PR and exits.

  • A slot is one running agent. policy.concurrency caps them (2 by default). A brief holds one slot for its writer and reviewer together. Verifiers take slots too, and the ready and pre-verify commands of a claim take one slot, all of them together. The other checks, rebases and merges do not.
  • A slow tick is logged. A tick that takes longer than policy.tickSeconds logs tick-slow with the numbers of its line, at most once in ten minutes. It is no error and sends no notice.
  • The gate runs before slots are handed out. A conflict it finds on a high-priority PR then competes for a slot in the same tick, ahead of new briefs for lower-priority PRs.
  • The fetch, the dependency check and the base watch belong to no PR. A failure logs its event, and the rest of the tick runs. None of them count against a PR, and five failures in a row of one step notify you.
  • Errors belong to one PR. Every per-PR step runs inside guarded(). An error becomes an error event for that PR and the tick goes on. A PR counts one error per tick, and the count resets after a tick without one. Five erroring ticks in a row, with no agent running, escalate that PR alone, once. Any other error is a tick-error event, and the next tick starts as usual. Five failed ticks in a row notify you once.
  • An outage is nobody's error. When GitHub or the network is down, a failed call counts against no PR and no step, and fires no five-in-a-row notice. The tick logs one github-unavailable event and tries again on the next tick. A start during an outage goes on, and logs the fetch or label call it lost the same way. After 30 minutes in a row you get one notice, and one more when GitHub answers again (github-back).

The PR lifecycle #

Every PR in the manifest has a stage and a status in the ledger. The stage says where the PR is, and it moves forward through the six below. A fix, a new head or a block sends it back. The status names what happens on the stage, and each one has a row in the table of the next section.

Stage What happens What comes next
brief The PR has no brief file. It waits for its dependencies and a free slot, then a read-only writer drafts the brief from briefing.sources on a worktree of the base, and a read-only reviewer checks it against the code and returns the final text (brief-write, then brief-review). A dependency that is verified but not merged yet is merged into a preview worktree, <id>.brief next to the PR worktrees, at its verified head. So the brief is written while the dependency waits for approval. The preview is detached, refuses every push and is removed after the reviewer. The reviewer also sees your answers to earlier drafts. With gates.brief criteria, both see them and the reviewer reports each one. With gates.brief.runChecks, the reviewer runs the draft's existing commands in that worktree and reports whether each can pass after a change within the expected files. The brief keeps the gates.brief it started with, also when the manifest changes meanwhile. The driver writes the brief file and a .review-notes.md file next to it, and the PR moves to implement. Open questions: brief · needs-you: brief-questions, and no brief is written. With gates.brief, a required criterion that does not pass and a check that cannot pass each add a question, unless the reviewer asked one that names the criterion's id or quotes the command. A recommended criterion that does not pass goes into the review notes. Each check and criterion logs a gate-check event with stage brief, its item, level, result and evidence, and ahead, the dependency heads the brief saw (empty on the base), instead of a SHA. A failed run waits on brief after a backoff. Heads that do not merge cleanly in the preview wait on dependencies-merge with the attempt given back (brief-waits), until a dependency merges or is verified at another head. A dependency that merged with another patch than the brief saw is named in the implementer's prompt, and the code wins over the brief there.
implement With a brief, the PR waits for every dependency to merge and for a free slot. The implementer then codes in the PR's worktree, pushes, opens the PR and waits for CI (implement). Its self-check before READY runs the ready commands at the head it reports, and the READY report lists each one with its exit code in gates. A fix the PR owes waits for a slot with its reason and a note that explains it, then runs in the implementer's own session, resumed with the reason (fix). Without a session, a fresh one gets the whole protocol again. A READY report that names an open PR from the branch into the base: pre-verify. A READY report that does not match GitHub: a fix. A READY report GitHub could not read waits on pre-verify · waiting: github and is checked again on a later tick (report-unchecked), with no agent run. BLOCKED: decision or obstacle. A run that ends without a report (a crash, a stop, a stall, a timeout or an outage) owes a no-report fix, and the next tick resumes it as a fix run. A first implement run that lost its session starts again instead. A fix run that fails or is stopped keeps its reason and note, so the next fix run names them again. A PR with no brief file and no GitHub PR goes back to brief instead, so the brief writer runs first.
pre-verify The driver checks the claim itself. It re-reads the PR head, waits for CI on that exact SHA (ci), then applies the rollout policy to the diff. Then it reads the new code scanning alerts on the head. With gates.preVerify.scope, it then checks that every changed file outside the PR's scope is listed in the READY report's deviations. With ready or pre-verify commands, it then runs them itself in a slot, in the worktree at that head (under sandbox.runtime: docker each command in a container of its own), one at a time, in this order: gates.ready.required, gates.ready.recommended, gates.preVerify.required, gates.preVerify.recommended (commands). Only its own result for a ready command counts, whatever the READY report says. A failed required command of either stage ends the run. Their results stay with that head, on the card and the PR page, and a failed recommended command also reaches the verifier's prompt. A stop, or a claim that moved on while they ran, drops the results. A run that throws logs on-done-error and backs off like a failed agent run. When a stop, a crash or an error cuts a run short, the driver cleans what it left in the worktree on the PR's next step, before an agent or a command works there, so the clean-tree check does not count it against the implementer. With gates.verify.externalFindings, the last step before the verifier, after the commands, waits for the review's check run on that head (external-review), then reads its review.json and keeps the result for that head. Each check with a result logs a gate-check event with its stage (ready for a ready command, preVerify for every other check before the verifier), the item (ci, policy, code-scanning, scope, external-review, or the command itself), its level (required, or recommended for a recommended command), the result, the short SHA and short evidence. The result is pass, fail, or skip for code scanning that is off or unavailable and for an external review that gave no result. A ci pass lists every run on the SHA, apart from those repo.ignoredChecks names and the review's run, with its conclusion. A command's evidence is its summary, such as exit 1, then as much of the end of its output as fits. A pass or skip is logged once per claim and head, and a READY report or any new head starts a new list. A fail is always logged, a required one right before the send-back or block it causes. Only a required fail starts the list over, so the next round of checks logs every result again. Before the ready and pre-verify commands and before the verifier, the driver deletes untracked .claude/settings.json, .claude/settings.local.json and CLAUDE.local.md at the root of the worktree and logs local-config-removed with their paths. A global gitignore can hide them from the clean-tree check. A note that still waits for the implementer: a fix, before any check. CI green, no policy violation, no new alert, no undeclared file out of scope and a free slot: verify. With ready or pre-verify commands, the slot goes to them first, and the verifier starts on a later tick when no required command failed at that head. With the external review on, the claim then waits on external-review while the review's run may still give a result. A result, or a skip for a review run that failed, ran too long or left nothing the driver can read, goes on to the verifier. A failed required ready command: a fix, as ready check, with what the READY report claimed for it in the note. A failed required pre-verify command: a fix, as pre-verify check. CI red, CI still unsettled after ciStallMinutes, a violation or a new alert: a fix. With the scope gate on, an undeclared file out of scope: a fix. A new alert under codeScanning.action: block: code-scanning-alerts, and the claim check reads the alerts again on every tick until they are gone. An alert from an analysis of an older commit: it stays here and waits for the analysis of the head. A criteria catalog that is missing from origin/<base> or invalid when the verifier would start: it stays here with an error event, no verifier starts, and five erroring ticks in a row escalate it.
verify A fresh read-only verifier tries to refute READY for that SHA (verify), against the brief's acceptance checklist and the recorded decisions. Where a decision conflicts with the brief, the decision wins. With gates.verify, it also checks the project criteria, which the driver fixes when it starts the verifier, and reports each one as pass, fail or unverifiable. With gates.verify.criteriaFrom, the catalog entries that apply to the PR join them as required criteria. The driver reads the catalog from origin/<base> each time a verifier starts. After a FAIL it also re-checks the previous findings and the implementer's answers to them, as claims. A PR whose commands passed, or whose verifier was cut off, waits here for a slot. The next verifier re-checks the claim first, and on the same head and command lists it starts without running the commands again. The driver first judges the verdict by those criteria. A required one that does not pass, or that the verifier does not report, is a finding, and a PASS with one counts as a FAIL. A recommended one never blocks. PASS from an untouched worktree for the claimed SHA: merge. FAIL: a fix, or verify · needs-you: dispute when a finding the implementer disputed is still open. A PASS from a verifier that changed the tree is discarded, and the PR waits on verify · waiting: slot for the next verifier, or goes to a fix when a note waits in the queue. A PASS for a stale SHA is discarded too: pre-verify. When the verifier touched the tree, the driver resets it to the SHA. It first deletes the same untracked Claude Code files as before the verifier and logs local-config-removed when there were any. After verify-done and any reset, and before the event of the outcome, each criterion logs a gate-check event with stage verify, its id as the item, its level and its result: pass, fail or unverifiable. As before the verifier, a result other than fail is logged once per claim and head. verify-done keeps the verifier's own verdict.
merge The verification is bound to the head SHA and the patch id. The gate runs on every tick, and its verdict sets the status (the merge gate). Gate merge: merged. Rebase: the driver rebases the branch itself. Fix, a conflict or a maintainer review: a fix. Block: gate-blocked. A new head with a different patch: pre-verify. A patch id the gate no longer matches, on the same head too (not-verified): pre-verify.
merged Merged by the driver, or on GitHub by you. The PR's clone and the remote branch are removed. When an agent still runs, that waits until its run ends, and its report is ignored. Final.

A needs-you status waits for you on any stage. A question from the agent (decision, obstacle) or about the brief (brief-questions) waits for rollout note. An answer to brief questions gives the brief attempt back. A question waits for your words, so rollout retry is refused there. On an obstacle, retry sends the PR to a fix run with the reason retry and fresh attempts. With policy.delegate on, the delegate may answer first. An agent sure that a code scanning alert is a false positive blocks with kind code-scanning, which never goes to the delegate. After that report, dismiss a false positive on GitHub and retry.

A code scanning block of the driver's (code-scanning-alerts), a gate block (gate-blocked, for example the release PR or a draft) and a PR closed on GitHub (closed) need no command. The driver reads them again on every tick, and the PR moves on once the alert is dismissed, the gate passes or the PR is open again. A code scanning block keeps the verification. rollout retry on them only resets the budgets. A reopened PR gets back the status the close replaced, a question or a dispute with its time included, or else the waiting status of its stage. A note on a closed PR is kept, and after the reopen it applies as a note on the status the PR has again.

The driver gives up on a PR until you act when the attempts of a role ran out (attempts-exhausted), when the PR had an error in five ticks in a row (errors), or when the verifier still finds open a finding the implementer disputed, which is yours to decide (dispute). An outage never counts toward the five. rollout retry resets the attempts. Exhausted attempts wait for a slot on their stage, with any fix the PR owed, and errors go back to what the stage waits for. A PR on brief whose brief file exists moves on to implement instead. A PR whose verification still holds goes back to merge. rollout note sends an answer to a fix run, with one fresh attempt. A fix the PR owed keeps its reason, and the note joins it. On a PR still on brief with no brief file, the note goes to the brief writer instead. After a disputed finding only a note decides: it sends the PR to a fix with the findings, recorded as your decision on the dispute. Retry is refused there.

One hold sits beside the stage and status, in two scopes. hold sets it and release lifts it. Each hold records who set it (maintainer or driver), since when, and a reason when there is one.

  • A PR's hold is set on the PRs you name. Such a PR gets no new runs, rebases, ready notices or merges until release. A running agent finishes its step. Sync and feedback still run. A PR that depends on the held one gets no brief until release or the merge. A brief already running finishes.
  • The rollout's hold is set by hold --all, or by the driver itself after an account limit. No new runs start and nothing merges. Running agents finish.

The two stay apart. release --all lifts only the rollout's hold, and its released event names the PRs still held on their own. release P1 never lifts the rollout's hold.

Stage and status #

What rollout status, rollout card, the board and the PR page show is a stage and a status. The driver writes both into the ledger. The CLI and the UI migrate an older ledger in memory as they read it, and never write the file. The stage says where the PR is. The status says what happens there, in one of three kinds: running (an agent or the driver works on it), waiting (it waits for something that needs nobody) and needs-you (it waits for you).

Stage What happens there
brief No brief file yet. The brief writer drafts the brief and the reviewer checks it.
implement The implementer works on the PR, or fixes it. A fix names its reason.
pre-verify The driver checks the READY report against GitHub, waits for CI and code scanning on the claimed head, runs the pre-verify commands, and waits for the external review of the head when it is on.
verify The verifier checks the claimed head.
merge The merge gate decides on the verified head: the PR waits, asks for your approval, or merges.
merged Merged by the driver or on GitHub. Final. A merged PR has no status.

Each status has one sentence, the same in the CLI and the UI, from lib/sentences.ts. A part with no value drops out, and times read YYYY-MM-DD HH:MM UTC. A question shows its first line in the sentence and in full on the card and the PR page. A question the delegate handed back ends with what it did, with the first line of its reason: (the delegate passed it on: reason) when it escalated, (the delegate failed: error) when its run failed. Every needs-you status names its way out: what takes it away. A waiting: held status names the release.

driver-stopped is the one status the driver never writes. With no driver running, a stored running status shows as waiting: driver-stopped on the same stage, since the last heartbeat, because a stopped driver runs nothing. The headers of rollout status and the UI say since when the driver is down.

A hold turns a waiting status into waiting: held. A running or needs-you status stays as it is and carries a held marker: [held] after the status in the CLI, a held badge in the UI. The rollout's hold wins over the PR's own, as in the driver's tick.

On GitHub, the driver labels each open PR rollout-stage:<stage> and rollout-status:<code>, from the stored status. A PR with no number yet gets no label, and a merged PR loses them on the next sync. On its next sync the driver also removes the labels of older versions, rollout-stage:<state> and rollout-reason:<why>, from each open PR.

Roles #

Every agent is the same claude -p binary with a different prompt, session, set of permissions and report schema. The prompts live in prompts/ and the schemas in schemas/, in the skill's directory.

Role Prompt Session May Reports

brief reviewer brief-review.md, the sources, every earlier question with your answer, the gates.brief criteria, the writer's brief without its questions and notes new The same as the writer. With gates.brief.runChecks it runs the draft's existing commands and leaves the worktree as it found it. brief.json
implementer implement.md: the protocol, the brief and the recorded decisions after it, the verify recipe, the scope, the forbidden paths new, kept as the PR's session Edit, commit, push its own branch, open and edit the PR, wait for CI. ready.json
fixer fix.md: the reason, the note, the current head the implementer's, with --resume The same as the implementer. ready.json
fixer, fresh resume-fresh.md, which wraps the whole implement prompt new, when the old one is gone The same as the implementer. ready.json

No edits, commits, pushes or GitHub writes. verdict.json
delegate delegate.md: the question and evidence, the sources, the brief and earlier answers new, every time The same as the verifier. delegate.json
  • Effort comes from the PR's effort and rises on retries. The implementer goes up one level per attempt after the first. Fix runs use the implement effort and go up from the third fix attempt. The verifier keeps effort.verify, and briefs use effort.brief (xhigh by default).
  • Budget. Every run gets --max-budget-usd from policy.budgetUsd for its effort. There is no cap for a whole PR or rollout.
  • Model. Every role runs the manifest's model, opus by default.

The delegate

The delegate is off unless policy.delegate is set. When a PR blocks on a question of an allowed kind, brief questions and needs-decision by default, the driver starts it in a free slot. The PR shows running: delegate on the question's stage while it runs.

It reads the question and the evidence, the plan and design notes, the brief, every earlier answer and the code. It answers only what the plan decides, and escalates the rest: a silent or ambiguous plan, security, credentials, publishing, releases, weakened tests, code scanning, a wider scope. An answer reaches the agent the same way your note does, prefixed as the delegate's. An escalation hands the question back to you as its needs-you status, and so does a failed run. The sentence then names the delegate's reason or the run's error. When the delegate takes a question, the blocked notice is skipped and its answer or escalation is the one notification. It comes after the run, so it also waits for a free slot.

Each question gets one run, also when that run fails, and a PR at most maxPerPr runs. A note of yours always wins. It applies at once, also while the delegate runs, and the delegate's late answer is dropped. A delegate run a stop or a restart cut off gives its run back and hands the question back as it was, and the delegate may take it again.

One agent run #

The driver talks to a running agent in two ways. It writes the prompt to the agent's stdin, and it reads the agent's stdout and stderr. Everything else the agent does goes through the worktree and GitHub, where the driver checks it. Under sandbox.runtime: docker the agent runs in a container, and its stdin, stdout and stderr pass through the docker client.

The command

The prompt goes in on stdin, because briefs and brief sources get large. The working directory is the PR's worktree, a clone of its own. 

claude -p --model <model> --effort <effort> \
  --output-format stream-json --verbose \
  --json-schema <schemas/ready|verdict|brief|delegate.json> \
  --permission-mode auto --permission-prompts none \
  --settings <deny and allow rules, the guard hook> \
  --setting-sources project --strict-mcp-config \
  [--mcp-config <mcpConfig>] # implement and fix only
  --disable-slash-commands \
  --tools Bash Read [Edit Write] WebFetch WebSearch TaskStop # Edit and Write for implement and fix
  --max-budget-usd <policy.budgetUsd[effort]> \
  --disallowedTools [Edit Write NotebookEdit] # the file tools for the verifier, brief and delegate roles
                    ScheduleWakeup CronCreate CronDelete CronList RemoteTrigger Monitor
  --session-id <new uuid> | --resume <the PR's session>

Under sandbox.runtime: docker the same argv runs as the command of a docker run. The clone and the skill directory sit at their host paths, so --settings, the guard's hook command and the git hooks path are the same inside. The entrypoint sets the firewall as root and then runs claude as your uid and gid, with no capabilities and only the named variables. The image's claude runs, so claudeBin and repo.pathPrepend do not apply. See sandbox. 

docker run --rm --init --pull never --name rollout-<name>-<run> \
  --cap-drop ALL --cap-add NET_ADMIN … \
  --memory <memory> --cpus <cpus> --pids-limit <pidsLimit> -i \
  -v <clone>:<clone> -v <skill>:<skill>:ro -v <home>:/home/agent -w <clone> \
  -e HOST_UID=… -e HOST_GID=… -e ALLOWED_DOMAINS=… -e ROLLOUT_ENV=… -e GH_TOKEN -e … \
  <image> claude -p …
Environment
Under the host runtime, yours, with repo.pathPrepend first on PATH, plus ROLLOUT_ROLE and no other ROLLOUT_* variable, GH_REPO pinned to repo.github, no GH_HOST and no npm credentials. With a bot token also its GH_TOKEN, an empty GITHUB_TOKEN, a GH_CONFIG_DIR that points at an empty directory and GIT_TERMINAL_PROMPT=0. Every agent gets CLAUDE_CODE_DISABLE_AUTO_MEMORY=1, and the verifier, the brief writers and the delegate CLAUDE_CODE_PROMPT_CACHE_TTL=5m. Under Docker only the named variables arrive, see Security.
Context
The prompt, the repository's CLAUDE.md and the tools of the role, nothing you installed: no MCP server but mcpConfig for implement and fix, no skill and no auto-memory. An MCP tool never passes the guard, so a server that writes files or posts would break the read-only roles. All of it would be sent with every request of every run. On a subscription Claude Code writes the prompt cache for an hour by default, at twice the input price instead of 1.25 times. The read-only roles never pause that long between turns, so they get five minutes. Implement and fix keep the default, because they wait for CI and a fix resumes the implementer's session. Security has why the tools are an allowlist.
Settings
Deny rules for merges, reviews, repo admin and publishing, allow rules per role, attribution off, and a PreToolUse hook that runs hooks/guard-bash.mjs on every Bash call. With --setting-sources project, the project's .claude/settings.json loads too, but not .claude/settings.local.json, CLAUDE.local.md or your user settings. Security has the details.
Watchdogs
No output for policy.stallMinutes (20) ends the run, and so does the role's policy.timeouts. Both count awake time, checked once a minute. A check that comes more than a minute late counts the gap as sleep, so a sleeping machine kills no run. SIGTERM first, SIGKILL 10 s later. Under Docker the SIGTERM is docker stop -t 10 and the SIGKILL is docker kill, because a signal to the docker client alone does not reliably end the container.
One turn
A headless run ends with the agent's turn. An agent that ends a turn to wait for a background command, a subagent or a wakeup is asked for its report at once and is cut off. So every prompt tells the agent to wait in the foreground, and the tools that act in a later turn are disallowed.
Transcript
stdout goes unchanged into logs/<id>-<NN>-<role>.jsonl. The UI shows it on the PR page's runs tab. A transcript that cannot be written does not stop the run. The driver logs log-failed once for that run, with the error.
Result
The last type: "result" line carries structured_output (the report), total_cost_usd, session_id and the permission denials. A run without that line, with is_error, or without a report has failed. The driver also reads claude's API error lines (is_api_error_message with an error kind) and rejected rate_limit_event lines. They tell an outage or an account problem apart from a real failure. The agent's own result text is shown as the error but never classifies it. stdout is read as one UTF-8 stream, so a character split between two reads arrives whole. A last line without a newline counts like any other.

The reports

--json-schema makes the agent end with a JSON document in a fixed shape. The driver acts on a few fields and checks what it can on GitHub and in the worktree. The rest goes on the card for you.

Schema Used by Fields
ready.json implementer, fixer status (READY or BLOCKED), summary and gates are required. gates has one entry per ready command of the self-check, with the command, its exit code and the end of its output, and is empty without ready commands. READY also needs pr and headSha, which the driver checks, not the schema. blocked with a kind, a question and evidence for BLOCKED. Optional: checks, localVerification, checklist, expected, filesChanged, changeset, deviations, and addressed for review comments and verifier findings. An entry for a finding also has outcome, fixed or disputed.
verdict.json verifier verdict (PASS or FAIL), sha, summary, checklist with pass, fail or unverifiable and evidence per item, blocking, nonBlocking, recheck with resolved, open or wrong and evidence per finding to re-check, and criteria with pass, fail or unverifiable and evidence per project criterion. recheck and criteria are empty when there is nothing to report. All required.
brief.json brief writer, reviewer brief (markdown), expectedFiles, changesetBump, questions, notes, checks with the command, exit code (-1 when it did not finish), whether it can pass and evidence per command the reviewer ran, and criteria with pass, fail or unverifiable and evidence per gates.brief criterion. All required. checks and criteria are empty when the prompt asks for none, and always from the writer. The expected files become the PR's scope when the manifest has none.
delegate.json delegate decision (answer or escalate), answer (empty for escalate), planRefs and reasoning. All required. The answer goes to the agent, the rest to the card.

How a fix resumes

A fix run resumes the implementer's session with --resume, so the agent keeps everything it knew. Its prompt names the reason (for example CI is red, rollout policy, code scanning, verifier findings, rebase conflict or maintainer review), a note with the details and the current head. A fix from the merge gate names its cause the same way. A note you queued is appended. If the session is gone, the driver drops it, and the next fix starts a new session with the whole implement prompt inside resume-fresh.md. That prompt lists every recorded decision after the brief, oldest first, so the new session loses none of them.

After a verifier FAIL the note numbers the blocking findings F1, F2 and on, the verifier's own first, then each required project criterion that did not pass. The implementer answers each one in addressed: fixed, with the evidence, or disputed, with its reason. The driver keeps the answers of every READY report until the next verdict, so a CI fix in between loses none. The next verifier gets the findings and the answers after the brief and the decisions, as claims to check. It reports each one as resolved, open or wrong, and an open one blocks a PASS. When a finding the implementer disputed is still open, the PR waits for you on dispute instead of another fix round. Every FAIL numbers its own findings from F1.

The merge gate #

judge() in lib/judge.mjs is a pure function of facts the driver read from GitHub and git. It never looks at what an agent said. The driver reads the git facts with the global and system git config off and every diff option stated. File names come NUL-separated, and added lines are read by their hunk counts from a diff with --text. The patch id is computed from the bytes of the diff, with full blob ids. A read the driver cannot parse is an error of that PR, never a fact.

For a verified PR judge() returns one action: merge, rebase, fix, wait or block. It checks, in this order:

  1. Wait while the PR is held.
  2. Block when there is no PR for the branch, the PR is closed, it is the release PR (repo.neverMerge), it is a draft, its base or head branch is wrong, or the rollout label is missing. A PR merged on GitHub while the gate reads it waits instead, and the next sync records the merge.
  3. Wait for dependencies, and for a verification of the current patch id. A verified PR whose patch id no longer matches goes back to be verified again (not-verified).
  4. Wait for approval, with policy.merge: human only. With policy.approval: github and a PR that no maintainer authored, that is a maintainer's GitHub review submitted after the current patch appeared, with no changes requested. Otherwise it is rollout approve for this patch. In manual mode your own merge is the approval, and auto needs none.
  5. Fix on a policy violation: a forbidden path, .github/ without allowWorkflows, .claude/ without allowClaudeConfig, a package version edit, a removed or missing changeset, a bump above maxBump, a denylisted term, or a commit with more than one line.
  6. Wait while the base branch is red (base-red). Nothing is rebased onto it, sent back for its failure or merged until it is green. An approval can still be given meanwhile.
  7. Rebase when the branch is behind the base or conflicts with it.
  8. Wait until GitHub reports the PR as mergeable.
  9. Fix when CI is red on the head. Wait while it is pending or a required check has not appeared.
  10. Fix or block on new code scanning alerts at or above repo.codeScanning.minSeverity, as its action says. Wait while an alert comes from an analysis of an older commit. A fix run sure of a false positive reports BLOCKED with kind code-scanning, which only you answer.
  11. Wait while the base branch's CI still runs (base-pending).
  12. Wait for GitHub's own merge state, unless the merge uses --admin or the mode is manual. It must be clean, or has hooks, or unstable. BLOCKED usually means a ruleset requirement such as a review or code scanning results.
  13. Merge. In manual mode the driver notifies you that the PR is ready to merge instead.

Every verdict carries a code beside its action. The driver decides on the code, never on the reasons, which are prose for you. It logs a gate-<action> event with the code and the reasons when the action or the code changes. The codes awaiting-github-review, stale-github-review and awaiting-inbox-approval send the approval notice once per patch. github-blocked sends the ruleset notice once per head. The last three codes below are the driver's own, for manual mode and a refused merge.

Code Action When
held wait The PR is held (rollout hold). The reason names who held it, as in held by maintainer (rollout release P1).
no-pr block No PR exists for the branch.
merged-on-github wait The PR was merged on GitHub. The next sync records it.
pr-not-open block The PR is closed.
never-merge block The release PR (repo.neverMerge).
draft block The PR is a draft.
wrong-base block The PR's base is not repo.base.
wrong-head block The PR's head is not its branch.
missing-label block The rollout label is missing.
deps-pending wait A dependency is not merged yet.
not-verified wait No verification of the current patch. For a PR on merge the driver drops the verification and sends the PR back to pre-verify, and logs head-moved-reverify with reason not-verified. Under merge: human the approval was for the old patch id, so it is asked for again after the next PASS.
awaiting-github-review wait No maintainer approved on GitHub yet.
stale-github-review wait The GitHub approval predates the current patch.
changes-requested wait A maintainer requested changes on GitHub.
awaiting-inbox-approval wait No rollout approve for the current patch.
policy-violations fix A policy rule is broken.
base-red wait The base branch is red. Merges, rebases and fixes from the gate wait until it is green. A check run that says nothing about the code, such as Dependabot's update job, goes on repo.ignoredChecks in the manifest. The edit applies on the next tick, with no restart.
behind-base rebase The branch is behind the base or conflicts with it.
mergeable-unknown wait GitHub has not reported the PR mergeable yet.

Each verdict becomes the PR's status. A wait or a code that asks you for something is a status on merge that the gate replaces on its next run, for example held, dependencies, ci, base-red, approve, review or merge-by-hand. A block is needs-you: gate-blocked with its code, or code-scanning-alerts, and the gate reads it again on every tick. A fix goes to implement · waiting with the reason policy, ci-red or code-scanning. A rebase waits for CI on the new head, and a conflict goes to implement with the reason rebase-conflict. A merge is running: merge until the PR is merged. Only merge-refused waits for rollout retry. not-verified sends the PR back to pre-verify, and merged-on-github lasts until the next sync records the merge.

With merge: human the driver then waits policy.mergeDelaySeconds (120 s), counted from when it first sees the approval, so rollout hold P1 can still stop it. A dry run logs would-merge and stops there. Otherwise it merges the exact head it judged: 

gh pr merge <n> --<method> --match-head-commit <sha> \
  --subject "<title> (#<n>)" --body "" [--admin] # method: squash by default
  • --admin is added when repo.merge.admin is true, or when it is auto and a maintainer authored the PR, because GitHub does not let authors approve their own PR.
  • GitHub refusing the merge is a state to wait in, not an error. The gate records it and you get a notification. The PR waits on merge-refused until rollout retry, so the driver does not try the merge on every tick.
  • A merge GitHub has not confirmed, accepted but with no merge commit to read yet (a merge queue, for example), logs merge-unconfirmed. The PR stays verified until the next sync sees it merged. Then the driver records the merge, notifies you and cleans up. Nothing is removed before that.
  • Rebases are the driver's own work. It rebases the judged head onto the base in the worktree and pushes with --force-with-lease on that head, as the bot. A conflict aborts the rebase and goes back to the implementer with the conflicting files. When the patch id stays the same, the verification and the approval carry over to the new head. Under the Docker runtime the rebase and its push run in a container over the clone, with the bot's token, like every git command the driver runs in a PR's clone once the clone is set up.
  • The release PR ("chore: version packages" by default) is never merged, because merging it publishes. After the last PR, the driver finds it by title and tells you to merge it.

Failures and recovery #

The driver has to keep going for hours, unattended. This is how it treats what goes wrong.

What happened What the driver does
A run that did no work Stopped by the driver, a transient error (rate or usage limit, overload, HTTP 429 or 5xx, a dropped connection, claude's rate_limit, overloaded or server_error, a rejected rate_limit_event), an account error, or under $0.01 and under 60 s. The attempt is given back, at most five times per PR. rollout retry starts that count over.
Any failed run Backs off before the next one: 2, 4, 8, 16, then 30 minutes. The streak resets on a successful run. A stop by the driver does not count. rollout retry starts the streak over.
Attempts ran out policy.attempts caps each role (implement 2, fix 4, verify 3, brief 2). The next launch escalates the PR. A verified PR gets its verify attempts back.
Errors in five ticks in a row A PR counts one error per tick, and a tick without one starts the count over. After the fifth erroring tick in a row, guarded() escalates that PR as soon as no agent runs for it. An escalated PR is not escalated again. The other PRs go on. An outage never counts, and a tick that only met an outage leaves the count as it was.
A driver-wide step failed A failed fetch, outside-dependency check or base watch logs fetch-failed, outside-deps-failed or watch-base-failed and counts against no PR. The rest of the tick runs, except the gate after a failed fetch. Five failures in a row of one step notify you. An outage never counts toward the five and logs no such event.
GitHub or the network is unreachable A GitHub request answers a 5xx or a rate limit, cannot connect, or gets no answer within 60 s. A git call fails with one of six of git's messages: "Could not resolve host", "Connection refused", "Connection reset", "timed out", "early EOF" or "The remote end hung up". The rules are githubUnavailable in lib/github.mjs, and the status and kind of a failed request come from lib/gh.mjs. Such a failure counts against no PR and no driver-wide step. The first one in a tick logs github-unavailable, and the next tick tries again. After 30 minutes in a row the driver notifies you once. The first tick with no outage logs github-back, and notifies you only if you got that notice. A 401, a 403 that is no rate limit, a 404 or a 422 is no outage, and counts as an error. So does a failed gh pr merge that gh does not call a refusal.
The machine slept The first tick after a wake logs machine-slept with the minutes slept. For two minutes, every failed GitHub request or gh or git call is an outage, because the network comes back a little after the machine does. Any other error still counts. Agent runs count only awake time, so the sleep runs down no timeout.
Five failed ticks Each failed tick is a tick-error event with the number of failed ticks in a row, and the next tick starts as usual. The fifth in a row notifies you.
A write that failed as a job ended The end of an agent run, a brief, a delegate or a pre-verify job never stops the driver. A ledger save or event write that fails there is printed to the driver's output. The next tick saves what the job changed, or fails like any other tick.
A READY report GitHub could not read The PR waits on pre-verify · waiting: github with a report-unchecked event, and the report waits. A later tick checks it again with no agent run and no attempt spent. A report that names a PR GitHub does not know still goes back to the implementer: the PR read answers 404 while the repository still reads. A 404 for both waits like any other error, because a token that lost access to a private repository gets one for each. A waiting report counts as an error of the PR on each later tick that fails, unless it is an outage.
A merge GitHub has not confirmed Logged as merge-unconfirmed. The PR stays verified and nothing is cleaned up until the next sync sees it merged.
A run ended without a report The PR waits on the stage of its run, with a no-report fix on implement, and resumes on a later tick. So does every run in progress when the driver stops. A fix run that fails, is stopped or is cut off by a hard end keeps its fix instead: the PR waits on implement with that fix, and the next fix run gets the same reason and note. It also gets the run's error, unless a hard end cut the run off. A brief run waits on brief again, and a delegate run hands the question back as its needs-you status.
The session is gone The driver forgets it, and the next fix starts a new session with the full protocol.
No output, or too long The stall watchdog and the role's timeout, both in awake time, kill the run. It ends as failed and the PR waits to resume on the stage of its run. Stderr from before the kill still counts, so a rate limit there gives the attempt back.
A run hit its budget cap It reached --max-budget-usd and fails with "hit its budget cap ($N)". It counts as an attempt, and the driver does not hold the rollout.
The base went red after a merge The driver logs base-red and notifies once. The gate waits with base-red, and agents go on. Merges start again by themselves when the base is green.
An account limit A spend limit, credit balance, billing or account budget error, or claude's billing_error, account_on_hold or authentication_failed, holds the whole rollout until release --all. The hold names driver and the run's error. A notification says so. A hold already in place stays as it is, a maintainer's included, and the notification still comes.
A broken manifest edit Rejected with a notification. The previous manifest stays in use. A missing manifest is rejected the same way, once.
GitHub refused the merge The gate waits and notifies. Nothing counts as a failure.
Code scanning could not be read A repo without code scanning answers 404 or 403. The driver logs code-scanning-unavailable once per PR and goes on without it. Any other error counts as an error of that PR, unless it is an outage such as a rate limit.

Maintainer feedback on GitHub #

You can review a rollout PR on GitHub as you would any other. The driver turns your comments into a fix run.

  • Only people in repo.maintainers count. It reads their inline review comments, review bodies (commented or changes requested) and conversation comments. With no maintainers set, it reads none. Comments that end with the driver's <!-- rollout-driver --> line never count, even under a maintainer's login (maintainerFeedback in lib/github.mjs).
  • Bot comments, such as code scanning or Copilot reviews, never count. Code scanning alerts reach the gate as data from the API instead.
  • It looks at every PR with a GitHub PR, at any stage and status, a question or a dispute included. While an agent or the pre-verify commands work on the PR, or the PR is closed, the comments wait unread until the run ends or the PR is open again.
  • It waits until you have been quiet for policy.feedbackQuietMinutes (3), so a review in progress is not cut short. Meanwhile the gate skips the PR.
  • Then the comments follow the rows of rollout note, with the reason maintainer-review where a note gives maintainer-note. Most rows send the PR to a fix run without its verification and approval. A fix the PR owes keeps its reason, and the comments join it. On a dispute the findings go to the fix run, with the comments as your ruling. The note holds every new comment, the file and line, and the code it refers to. The fixer lists each comment id in addressed, with what it did.
  • After the fixer reports READY, the driver answers each inline thread with that action and the new short SHA, as the bot. Without repo.agentToken the replies go out under your login. Everything else is summed up in one PR comment. Handled comments are remembered by id and never sent twice.

Notifications #

The driver sends each notice to every target of policy.notify that is on: the desktop, on by default, through osascript on macOS and notify-send on Linux, a shell command, and a webhook that gets a JSON POST. A failing target logs notify-failed once per target per driver run, and the driver carries on. Nearly every notice is also a line in events.jsonl. The gate's notices about a missing approval or GitHub still blocking show up there only as gate-wait with their code, awaiting-github-review, stale-github-review or awaiting-inbox-approval for an approval and github-blocked for GitHub (see the merge gate).

  • Waiting for you: verified (with the next step), blocked and brief questions unless the delegate takes them, escalated, ready to merge in manual mode, a question the delegate passes to you, the delegate's run limit for a PR.
  • Decisions: approval accepted or rejected, a GitHub approval the driver has seen, merged, would merge in a dry run, an answer from the delegate.
  • Trouble: the base red after a merge, held by an account limit, merge refused or blocked by GitHub, the head moved after verification, the verifier changed the tree, a dependency outside the run, a rejected manifest, five failed ticks in a row, five failures in a row of a driver-wide step, GitHub unreachable for 30 minutes, and GitHub back after that.
  • The end: all PRs merged, with the release PR to merge.

Notices that could repeat on every tick are sent once per patch or head, once per block, and once per outage. A merge GitHub refuses notifies once, because the driver tries it again only after rollout retry.
