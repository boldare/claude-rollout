Ship a plan of PRs with Claude Code agents

README.md

claude-rollout takes a plan that needs several pull requests and ships it. Headless Claude Code agents write each PR, an independent agent tries to refute it, and a merge gate re-checks everything on GitHub before anything merges.

Internal alpha. It shipped describe-me 0.5.0, 13 PRs, end to end. Expect rough edges and read the setup pages first.

How it fits together #

The orchestrator is a process, not a model. rollout run ticks every minute, reads the truth from GitHub, starts agents, runs the gate and records everything in a ledger. A stalled chat session cannot stall a rollout, and running the same command again resumes it.

  • You write the plan into manifest.yaml and send commands with the CLI or the web UI. Both drop them into inbox/.
  • The driver wakes on a new command or once a minute. It reads GitHub, updates ledger.json and starts agents in free slots.
  • Agents run as headless claude -p processes, each in the PR's own git worktree. They push and open PRs as a separate bot account and report back with a JSON document.
  • The driver never trusts a report. It re-reads CI, the diff and the reviews on GitHub, and merges only what its gate passes.

The full picture, with the tick, the PR lifecycle and one agent run, is on How it works.

One PR, four roles #

Every PR goes through the same agents. The colours are the ones the UI uses for runs on its timeline.

Brief writer and reviewer

A PR without a brief gets one from the plan. A read-only writer drafts it, a read-only reviewer checks every path and command against the code.

Implementer

Codes the PR in its worktree, pushes the branch, opens the PR, waits for green CI and reports READY or BLOCKED.

Fixer

The implementer's own session, resumed with the reason: red CI, a policy violation, verifier findings, a review or a conflict.

Verifier

A fresh read-only session that tries to refute READY against the brief's acceptance checklist, for the exact commit.

What stays with you #

  • The plan, and the answers when an agent or the brief reviewer asks a question. With policy.delegate on, the delegate answers what the plan decides and passes the rest to you.
  • Approval. A GitHub review or rollout approve, never an agent and never the UI.
  • The release PR. Merging it publishes, so the driver never touches it.
  • Pause, hold, retry and stop, when you want to step in.

Everything else is the driver's job: slots, worktrees, rebases, retries, the gate and the merges in dependency order.

Safety in short #

Agents push and open PRs as a separate GitHub account with the Write role and no ruleset bypass. A Bash guard, deny rules and git hooks keep them on their own branch. The gate decides on facts read from GitHub, never on what an agent says. The limits of all this are spelled out on Security.
